# FluxRT 双仿真共同契约 V1

## 1. 结论

P1.3 已让 Rust PC 与 MATLAB/Simulink 从同一套版本化文件读取仿真身份和场景，不再各自
手抄 524 rpm、板卡/电机身份或 D0/D1 规则。两端使用不同的生命周期 engine，输出统一的
结果清单，再由严格比较器逐字段核对。

这一阶段完成的是：

- **D0 身份一致**：文件哈希、板/电机/逆变器、运行配置 CRC、产品契约和 ABI 一致；
- **D1 离散生命周期一致**：状态、内部状态、来源、事件、输出和 fault 顺序一致；
- **legacy 场景迁移**：524 rpm 只在旧仿真适配边界换算，canonical 值为
  `54.873151 rad/s`；
- **篡改拒绝**：未知版本、缺字段、错误单位、身份或文件哈希不一致全部 fail-closed。

通用闭环仍未完成完整 D2～D4 连续波形、控制路径和故障数值对拍；P4.1B2 只先完成了
反馈传感器子系统的 D2～D4 对拍。两者都不是实机相关性证明。

## 2. 唯一 canonical 文件

| 文件 | 作用 |
|---|---|
| `simulation/contracts/legacy_speed_start.bundle.json` | 总入口；固定引用路径、identity 和每个文件的 SHA-256 |
| `simulation/contracts/fluxrt-simulation-v1.schema.json` | V1 顶层必需字段集合 |
| `simulation/profiles/stm32g431_gbm2804h_reference_v1.json` | 板/功率级/电机、时基和模型参数 |
| `simulation/scenarios/legacy_speed_start.json` | 524 rpm SI 场景、扰动和 D1 预期事件 |
| `simulation/scenarios/feedback_sensor_fault_matrix_v1.json` | P4.1B2 反馈传感器量化、延迟、故障矩阵和路由门 |
| `simulation/contracts/trace-schema-v1.json` | 后续 D2～D4 的 canonical 通道、单位和类别 |
| `simulation/contracts/comparison-gates-v1.json` | D0/D1 精确项、零 tick 容差和后续数值容差 |

Rust 和 MATLAB 都直接打开 bundle 引用的这些文件。bundle 路径必须是工程根目录内的安全相对
路径；文件字节哈希不一致时不得继续比较。

这里的 profile 名称带 `reference`：它是仿真共同输入，不是已批准 ProductionMotorProfile，
不能用 D0/D1 PASS 覆盖 A26 的参数真值和审批门。

## 3. D0 身份

两端结果必须精确一致：

- bundle/schema/profile/scenario/trace/comparison 的 id、revision/version 和 SHA-256；
- `board_id`、`motor_id`、`inverter_id`；
- 当前 bridge 默认运行配置 `CRC32=0x9835ee59`；
- 产品契约 `0x00010000`、bridge ABI `0x00160000`；
- 稳定 `source_revision`、`model_revision`；
- runner 动态注入的 `workspace_revision=<HEAD>[+dirty]`。

`source_revision` 是可提交的模型来源版本，不能写入一个永久带 `+dirty` 的旧 Git 值。
`workspace_revision` 由一键脚本在运行时读取，因此本轮未提交证据显示为
`7f918beb...+dirty`；提交后重跑将显示新的 clean commit。

Rust 还实际调用 bridge 默认配置和 CRC 函数，若 JSON 中的 CRC 与当前代码不符就拒绝加载。
MATLAB 读取同一值并与 V1 固定身份核对，最终由跨端比较器保证两端结果一致。

## 4. D1 生命周期

D1 事件结构固定为：

```text
control_tick
axis_state
controller_internal_state
active_source
event
output_enabled
fault_flags
```

`legacy_speed_start` 的 V1 事件是：

| tick | Axis | 内部状态 | 来源 | 事件 | 输出 | fault |
|---:|---|---|---|---|---:|---:|
| 0 | Disabled | Disabled | none | axis_ready | 0 | 0 |
| 1 | Startup | Alignment | product_command | start_requested | 1 | 0 |
| 30000 | ClosedLoop | ClosedLoop | product_command | observer_handover_complete | 1 | 0 |

Rust 与 MATLAB 各自根据 `command_at_s`、`startup_duration_s` 和 `control_frequency_hz` 运行最小
生命周期 engine；scenario 中的 `d1_events` 只作为 oracle 检查。测试会清空 Rust oracle 后
再次运行 engine，防止把“回显同一份 JSON”误报成独立对拍。两个结果的 engine id 必须分别为：

- `fluxrt.rust.lifecycle.v1`；
- `fluxrt.matlab.lifecycle.v1`。

D1 的 tick 容差为 0，状态/fault/输出类字段不能使用 RMSE 放宽。

## 5. 两端实现

Rust Host-only 实现在 `rust/crates/foc-sim/src/simulation_contract.rs`，使用自带严格 JSON
解析和 SHA-256，不给 `no_std foc-control` 或目标固件增加依赖。命令入口为：

```powershell
cargo run --manifest-path .\rust\Cargo.toml -p foc-sim --bin foc-contract-check -- `
  --root . --out .\simulation\results\contract\rust-d0-d1.txt
```

MATLAB 实现在：

- `simulink/load_fluxrt_simulation_contract.m`；
- `simulink/validate_fluxrt_simulation_contract.m`；
- `simulink/test_fluxrt_simulation_contract.m`。

它不启动 Rust 可执行文件，也不读取 Rust 结果生成自身结果。最终比较器
`simulation/compare_contract_gate_results.py` 只在两端独立完成后比较结果。

### 6.1 P4.1B2 反馈传感器 D2～D4 扩展

P4.1B2 沿用同一个 profile、trace schema 和 comparison gate，增加独立的 Rust PC 与 MATLAB
反馈传感器模型。两端都直接读取 `feedback_sensor_fault_matrix_v1.json`，但不互相调用、也不读取
对方结果：

- Rust：独立生成 ABZ/Hall 样本，并复用产品代码中的 `FeedbackRouter`；
- MATLAB：独立实现 ABZ/Hall 样本、路由和迟滞状态机；
- Python：核对 D0 元数据、D2/D4 离散字段、D3 连续量和 feature-off 语义。

一键命令：

```powershell
cd E:\File\RT-Thread\projects\FluxRT
.\simulation\run_feedback_sensor_gate.ps1 `
  -PythonExe D:\Environment\env-windows-latest\.venv\Scripts\python.exe
```

V1 场景共 5 个 case、80 行：feature off、nominal、编码器掉线后 Hall 回退、Index 缺失、
编码器掉线叠加 Hall 错序。最终门应输出：


## 7. 下一阶段怎么扩展

后续场景不得新建另一套参数约定。正确步骤是：

1. 复用或新增 versioned profile/scenario，并更新 bundle hash；
2. 在 trace schema 中先定义 canonical SI 通道；rpm 只能作为显示派生值；
3. Rust 与 MATLAB 分别实现模型，不互相调用结果；
4. D0/D1 先通过，再进行 D2 采样时序、D3 连续量和 D4 fault/降级比较；
5. `.slx` 中如保存 MATLAB Function 快照，必须把源码 hash/staleness 作为硬门；
6. 仿真报告记录 Git workspace revision、engine/model revision、场景/profile hash 和比较门版本；
7. 只有硬件 trace 使用同一 identity 和时基后，才进入 P2.3 三方相关性，不把 S3 写成 S5。
