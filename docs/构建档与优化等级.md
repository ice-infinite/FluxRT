# FluxRT 构建档与优化等级

## 1. 当前选择

日常开发默认使用：

```text
Profile = Diagnostic
RustOptLevel = s
```

原因不是单看体积：STM32G431 实机 5 秒开环对比中，Rust `s` 相对 `3` 回收约 5 KiB
Flash，完整 ISR WCET 只增加约 2%；`z` 只比 `s` 再节省 800 B，却使 WCET 增加约 7%。

`Production` 是可继续验收的生产候选构建档，不代表已经量产通过。它仍保持
`closed_loop_enable=0`，并保留立即关断、输出复核、过流、母线、驱动故障和 deadline
保护。A14 起三个构建档都会校验同一份编译期只读
`ProductionMotorProfile`；当前 revision 1 的审批位为 0，不授权闭环。

`Calibration` 是 A18 新增的停机采集专用档，不是可运行电机的调试档。它保留 A17
相电压固定窗，但不编入在线调参、实时 trace 或数学诊断，并在应用层和平台层两处
编译期拒绝 motor arm。

## 2. 三种构建档

| 能力 | Diagnostic | Calibration | Production |
|---|---|---|---|
| `foc_status` / `foc_stop` | 保留 | 保留 | 保留 |
| `foc_start` | 可用，仍受全部安全门约束 | 仅保留明确拒绝桩；平台层也拒绝 | 可用，仍受全部安全门约束 |
| 在线 `foc_cfg` 浮点调参 | 保留 | 裁剪 | 裁剪 |
| `foc_trace` 与 64 项环形缓冲 | 保留 | 裁剪 | 裁剪，API 返回未配置 |
| `foc_phase_capture` 与 4 KiB 固定窗 | 保留 | 保留 | 裁剪 |
| 停机数学诊断/基准 | 按 Kconfig | 强制裁剪 | 强制裁剪 |
| 同拍 WCET 与 deadline 保护 | 保留 | 保留；但不可 arm | 保留 |
| 默认闭环权限 | 关闭 | 编译期禁止运行 | 关闭 |
| 只读板卡/电机档案与 CRC | 开机校验，可停机临时调参 | 开机校验，无调参旁路 | 开机校验，无调参旁路 |
| 默认 Rust 优化 | `s` | `s` | `s` |
| 输出目录 | `cmake-build` | `cmake-build-calibration` | `cmake-build-production` |

Production 裁剪在线调参的原因是固定参数候选不应在运行现场被 Shell 任意修改；同时
`strtof` 会把 newlib 的 `strtod`、断言和格式化依赖链拉入镜像。裁剪 trace 则回收
3,072 B 环形缓冲及其 ISR/输出代码。

档位主宏和能力宏集中在 `foc/include/foc_build_profile.h`。CMake 必须三选一定义
`FLUXRT_DIAGNOSTIC_BUILD`、`FLUXRT_CALIBRATION_BUILD`、`FLUXRT_PRODUCTION_BUILD`；
若同时定义多个会编译失败。裸 SCons/Host 没有传档位时为了兼容既有流程默认 Diagnostic。
档位没有放进全局 `.config`，因为同一份 Kconfig 要能生成三套互不污染的 CMake 构建；
硬件、HAL 和算法候选开关仍由 Env/SCons/Kconfig 管理。

## 3. 常用命令

日常诊断构建：

```powershell
.\build.ps1 -Regenerate
.\build.ps1 -BuildOnly
```

Production 候选构建：

```powershell
.\build.ps1 -Regenerate -Profile Production -RustOptLevel s
.\build.ps1 -BuildOnly -Profile Production -RustOptLevel s
```

Calibration 停机采集构建：

```powershell
.\build.ps1 -Regenerate -Profile Calibration -RustOptLevel s
.\build.ps1 -BuildOnly -Profile Calibration -RustOptLevel s
```

重新比较 Rust 优化等级：

```powershell
.\build.ps1 -Regenerate -Profile Diagnostic -RustOptLevel 3
.\build.ps1 -Regenerate -Profile Diagnostic -RustOptLevel s
.\build.ps1 -Regenerate -Profile Diagnostic -RustOptLevel z
```

`-BuildOnly` 会检查所请求的 Profile/优化等级是否与 CMake cache 一致，不一致时拒绝
构建，避免把一个配置的固件误标成另一个配置。每个“档位 + 优化等级”都有独立 Rust
目录，例如 `build/rust-target-calibration-s`；CMake 显式链接对应归档，不能跨档复用
旧库。三档当前 Rust feature 相同，所以归档内容哈希相同是正常的，目录隔离仍是硬要求。

直接使用 SCons 时仍是 Diagnostic 语义，并使用 `rust/Cargo.toml` 的默认 `s`；日常 VS
Code 和 Production 构建统一走 `build.ps1`。

## 4. 实机采集

Diagnostic 支持 trace 关闭、10 Hz、50 Hz：

```powershell
python .\simulation\capture_timing_baseline.py `
  --profile diagnostic --port COM6 --rates 0,10,50 `
  --duration 5 --target-rpm 582 --allow-motor-run `
  --output .\simulation\results\timing-diagnostic.json
```

Production 已裁掉 trace，只能采集关闭状态：

```powershell
python .\simulation\capture_timing_baseline.py `
  --profile production --port COM6 --rates 0 `
  --duration 5 --target-rpm 582 --allow-motor-run `
  --output .\simulation\results\timing-production.json
```

脚本没有 `--allow-motor-run` 时拒绝启动；结束路径始终发送 `foc_stop`。闭环仍需另外
显式添加 `--closed-loop`，本构建档对比没有启用闭环。

## 5. 选择与发布规则

- 日常调参与波形采集使用 Diagnostic + `s`；
- `3` 只用于性能回归基准，不再作为默认，因为 Flash 余量不足；
- `z` 只作为尺寸下界，除非后续 Flash 压力超过 `s` 且重新通过 WCET；
- 发布候选使用 Production + `s`，但还必须通过独立速度/角度真值、故障注入、长测和
  多板多电机一致性；
- 切换 Profile 或优化等级后必须重新记录 BIN SHA-256、`text/data/bss` 和板端 WCET；
- 不得仅凭“构建成功”或“电机能转”标记为生产可用。

本轮具体数据见
[`performance/2026-09-23-A1构建档矩阵.md`](performance/2026-09-23-A1构建档矩阵.md)。

## 6. 2026-09-24 A13 当前基线

A12 ABI V6 后重新构建并做同口径开环实机对比：

| 指标 | Diagnostic + `s` | Production + `s` |
|---|---:|---:|
| ROM | 125,676 B（95.88%） | 94,620 B（72.19%） |
| RAM | 14,136 B（43.14%） | 8,872 B（27.08%） |
| 582 rpm 开环 5 s WCET | 8,906 / 12,500 cycles | 8,855 / 12,500 cycles |
| error / fault / miss | 0 / 0 / 0 | 0 / 0 / 0 |

Production 容量收益明确，但 WCET 只改善 51 cycles；它裁掉的是 trace/调参和格式化依赖，
并没有改变 Rust 控制主体。当前 Production 又因 `foc_cfg` 被裁掉而保持
`closed_loop_enable=0`，所以这组数字只代表开环，不能外推为闭环发布证明。完整证据见
[`performance/2026-09-24-A13-Production尺寸与开环WCET.md`](performance/2026-09-24-A13-Production尺寸与开环WCET.md)。

## 7. 2026-09-24 A14 参数档基线

A14 增加 ABI V12 规范化运行配置 CRC 和 40 B 只读档案。当前值：

```text
revision=1
board=0x43116001, motor=0x28041007
runtime CRC=0x8C7A8DF4, record CRC=0xD9F996C3
approvals=0x00, closed_loop_enable=0
```

| 指标 | Diagnostic + `s` | Production + `s` |
|---|---:|---:|
| ROM | 126,748 B（96.70%） | 95,700 B（73.01%） |
| RAM | 14,160 B（43.21%） | 8,896 B（27.15%） |
| 相对 A13 ROM | +1,072 B | +1,080 B |

Production 仍未开放闭环：CRC 只证明“实际字节与此档案一致”，不证明参数
已辨识、观测器已通过独立真值验证或固件已可发布。完整证据见
[`performance/2026-09-24-A14-ProductionMotorProfile.md`](performance/2026-09-24-A14-ProductionMotorProfile.md)。

## 11. 2026-09-24 CM3 Target 分层启用门

| 指标 | Diagnostic + `s` | Calibration + `s` | Production + `s` |
|---|---:|---:|---:|
| ROM (`text+data`) | 130,512 B（99.57%） | 99,240 B（75.71%） | 97,172 B（74.14%） |
| RAM (`data+bss`) | 18,728 B（57.15%） | 13,056 B（39.84%） | 8,936 B（27.27%） |
| Flash 余量 | 560 B | 31,832 B | 33,900 B |
| BIN SHA-256 | `0D62D11C...E1E66AF` | `BBDDBCD9...6AE5DDB7` | `2184C4EE...ABAD29ED` |

CM3 将模型以 ABI V13/config V7 接入了 target 快环，但总门/观测修正/PWM 前馈
默认仍为 `0/0/0`。三档 map 中 `feedforward_pwm`、`phase_voltage_loss_v`和
`observer_equivalent_pwm` 都有非零 Flash 地址，证明实现已连入而非只能编译。

无功率 S4 首次执行 `foc_cfg invstage 1` 时暴露了真实的 `tshell stack overflow`：
`foc_cfg` 原栈帧约 480 B，叠加 Rust 配置校验和打印调用链后超过 2 KiB FinSH 栈。
本轮没有扩大全局线程栈，而是把仅由 tshell 单写的 276 B 候选配置和 144 B 诊断快照
迁入静态管理区，修正后函数栈帧约 56 B；ISR 路径没有改变。

Diagnostic 因静态暂存区和失效安全诊断检查增至 130,512 B，只剩 560 B，后续不应再向
`applications/main.c` 增加大量 Shell 文本或浮点解析路径。修正版已经完成无功率 S4：
Calibration 的编译期拒绝门有效，Diagnostic 的 stage `0/1/2/3/4/0` 与 `FTIMING` V2
标签一致，且没有再次溢出。板上当前为修正版 Diagnostic `0D62D11C...E1E66AF`，重启后
恢复默认 `0/0/0`、Vbus 0 mV、输出关闭；完整 ISR WCET 和低压限流 A/B 尚未执行。详见
[`performance/2026-09-24-CM3-Target逆变器补偿配置与时序标签.md`](performance/2026-09-24-CM3-Target逆变器补偿配置与时序标签.md)。
