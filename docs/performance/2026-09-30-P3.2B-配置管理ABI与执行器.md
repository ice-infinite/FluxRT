# P3.2B 配置管理 ABI 与执行器

## 1. 结论

P3.2B 的软件架构门已完成：P3.2A 的纯 Rust 参数事务现在具有独立的 V1 C 管理 ABI、
固定容量上下文、无硬件 apply 执行器和 Fake Flash 故障闭环。既有实时 bridge V20、V19
快环输入、12 kHz ISR、电机参数和默认关闭行为均未修改。

本报告只证明 S1/S2。没有连接 RT-Thread 参数服务、目标 Flash、真实控制器/平台重建，
也没有烧录或运行电机，因此不能把“目标构建通过”写成“板端参数保存可用”。

## 2. 架构边界

```text
协议 / Shell / 测试客户端（后续）
             │ 固定结构、单写者
             ▼
foc_config_bridge.h  <->  foc-rt-bridge/config_abi.rs
             │ token + pending bundle + apply plan
             ▼
foc_config_apply_executor.c
             │ Platform -> Axis -> Management
             ▼
真实适配器（后续；本轮不存在）
             │ 全部成功后才 confirm_apply
             ▼
Rust commit write steps -> Flash adapter（后续） -> readback confirm
```

- 配置子 ABI 使用 `FOC_CONFIG_ABI_VERSION=0x00010000`，不提升实时 bridge V20；
- C 持有 2,048 B、8 字节对齐的不透明上下文，Rust 编译期断言实际上下文不会越界；
- 所有记录定宽、无指针字段；调用者指针只在一次 ABI 调用期间读取或写入；
- ABI 只允许管理任务串行调用，严禁 ISR、并发写者、动态分配和回调重入；
- 平台组（Board/Inverter/Calibration）先应用，随后重建 Axis，最后更新 App 管理策略；
- 任一动作失败即锁存 `FAILED`，不能调用 Rust confirm；复位仍需 Disabled、输出关闭、无故障；
- Flash 坏回读保留已经实际应用的 volatile active，但进入 `StorageFault`，后续 arm 返回 Busy，
  状态快照继续保留最初的存储错误详情。

## 3. 文件与职责

| 文件 | 职责 |
|---|---|
| `rust/crates/foc-rt-bridge/src/config_abi.rs` | 六组转换、ABI校验、定容上下文、事务/commit入口和错误映射 |
| `foc/include/foc_config_bridge.h` | C侧V1布局、状态码、尺寸断言和函数声明 |
| `foc/include/foc_config_apply_executor.h` | 无硬件执行器状态、动作和API |
| `foc/runtime/foc_config_apply_executor.c` | group→action映射、固定顺序、失败锁存和安全复位 |
| `tests/host/test_foc_config_apply_executor.c` | 三类计划、顺序、坏计划、乱序完成、失败与复位负例 |
| `foc-control/config_transaction.rs` | P3.2A事务真值源；P3.2B没有复制状态语义 |
