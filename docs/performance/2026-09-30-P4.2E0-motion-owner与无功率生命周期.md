# P4.2E0 motion owner 与无功率生命周期

## 1. 结论

P4.2E 的无功率前半已经完成到 S1/S2：新增一个默认关闭、无堆、无 RTOS/HAL 依赖的
motion 生命周期 owner，并用 Host fake 覆盖 owner/source、命令时效、序列回绕、timeout、
fault、disable 和 guarded recover。默认四档镜像保持与 P4.2D 完全相同，motion candidate
仍为 `n`，未进入 ISR、未连接 arm/MOE/CCR，也没有烧录或运行电机。

本阶段**没有完成 motion WCET**。临时 Diagnostic candidate-on 只能证明 C/Rust 候选可交叉
编译；因为没有真实消费者，management/adapter 大部分被 linker GC，不能把 +200 B 镜像差异
或 Host 时间写成完整 ISR WCET。

## 2. 新增边界

实现文件：

- `applications/foc_motion_management.h`
- `applications/foc_motion_management.c`
- `tests/host/test_foc_motion_management.c`

owner 的状态为 `Disabled -> Idle -> Active -> Failed`。初始化只配置 adapter，保持关闭；
`begin` 必须同时满足 V2 guard、Axis Disabled、输出关闭、无活动故障、非零 owner/source 和
1～60000 ms timeout。正常 stop 只有 owner 能执行；外部 fault、会话 timeout、命令过期或
motion core 错误都会先清安全输出、调用 `force_safe`、disable adapter，再锁定 Failed。

disable 不需要安全 guard，任何状态都能执行硬关断；但它不能清除 Failed/shutdown lock。
故障恢复只能在 Axis Disabled、输出关闭且无活动故障时执行，显式 disable 后恢复到
Disabled，未关闭功能门时恢复到 Idle。

## 3. 与 P1.2 的一致性

owner 不重新做权限仲裁，只消费已经仲裁的 `ProductCommand`，但保留来源、时间和序列的
防御性检查：

- `valid_until_ms` 是排他上界；
- `window = valid_until - created_at` 必须位于 `(0, 0x80000000)`；
- `age = now - created_at` 大于等于半范围视为 future/ambiguous 并 fail-closed；
- sequence 只接受非零且小于半范围的前向距离；
- `UINT32_MAX -> 0` 合法，恰好半范围拒绝；
- owner/source/sequence 拒绝不调用 adapter step，也不推进 planner/cascade；
- timeout/时间窗错误属于运行安全失效，会锁定 Failed。

## 4. 并发与最终目标接点

当前对象是**单执行上下文**服务。`step`、`poll` 和生命周期 API 都会修改同一
management/adapter，禁止未来由 ADC ISR 和管理线程同时调用同一实例。

真正目标接入必须再增加 dispatcher：

1. ISR 独占 realtime motion context；
2. 管理线程只发布固定大小命令快照及原子 stop/fault 请求；
3. observer/反馈更新之后、旧速度环选择 Iq 之前，在 Rust 内完成
   `motion -> current reference -> current PI`；
4. 不采用 C 侧 motion FFI 后再调用旧 realtime FFI 的双调用拼接；
5. timeout/fault 由单写者在同一拍清零并进入现有输出验证/commit 前的安全路径。

原因是机械反馈、observer 速度和当拍 Iq 目前都在 Rust realtime 内形成。把 motion 简单放在
C 调用前，会使用不完整或旧一拍反馈，还会增加两次 FFI 和共享 context 竞争。

## 5. 构建隔离

`applications/SConscript` 现在在 `FOC_MOTION_CONTROL_CANDIDATE=n` 时显式排除
`foc_motion_management.c`。`foc/SConscript` 仍只在同一开关开启时编译 adapter，
`custom.cmake` 只在 Diagnostic 传入 Rust `motion-control` feature。

默认恢复状态：

- `.config`：`# CONFIG_FOC_MOTION_CONTROL_CANDIDATE is not set`
- 生成的 `CMakeLists.txt`：无 management/adapter 源文件；
- 四档 map：motion management/adapter/Rust motion 命中均为 0；
- boot、Shell、Flash、ISR、arm、MOE、TIM1 CCR：均未连接。

临时 candidate-on Diagnostic：

- 构建通过；ROM 110804 B，RAM 22472 B；
- BIN SHA-256：`1DD22BF9FD62CD6538F8B2CCF4F0EA5E466C9E76B4836F30D5309D6387B4617F`；
- 比默认 ROM 多 200 B，RAM 不变；
- `nm` 只有 `foc_rust_motion_abi_version` 与
  `foc_rust_motion_context_required_align` 留在最终 ELF，owner/adapter 执行体被 GC；
- 因此没有 isolated step 或完整 ISR 的周期证据。

## 7. 未完成与下一步

下一步是 P4.2E1，不是直接让电机进入 Position：

1. 冻结 management task 与 ISR 单写者之间的固定快照/原子请求协议；
2. 在 Rust realtime 内建立 combined 接点，保持 motion 输出只能成为 Id/Iq reference，不能写 CCR；
3. 明确外环分频和真实 `dt`，不得直接把 12 kHz 配置隔拍执行；
4. 先做 stopped/bench-only 的 Torque、Velocity、Position transition/steady 周期测量；
5. 再测包含 command、feedback、motion、FOC、验证与 commit 的完整 ISR WCET；
6. 只有完整链满足 12750 cycles deadline 和阶段余量门后，才进入 P4.2E2 分模式 powered 验收。

当前最近同类完整 ISR 记录约 9763 cycles，只剩约 2987 cycles 到软件 deadline；这只是旧镜像
预算输入，不是本阶段实测。若 combined motion 无法满足预算，优先采用外环分频、单次 FFI 和
状态复用，不能通过放宽 deadline 或漏记 motion 周期过门。
