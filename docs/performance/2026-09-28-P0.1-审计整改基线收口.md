# P0.1 审计整改基线收口

## 1. 结论

P0.1 已完成源码、测试、四档目标构建和 Git 范围收口，可以作为后续 P1.1 公共契约
冻结的可回退起点。本轮达到的最高证据等级是 S2：没有烧录、串口操作、功率级使能或
电机运行，因此不更新板上固件结论，也不关闭 P0.2～P0.5 的目标安全与实时性任务。

开始基线为 `main` / `a216972b87d35ef090482e91f75f6a5f52d13b3c`。收口范围包含
2026-09-28 全量审计后的功率安全事务、同步 Vbus、C/Rust 锁存故障、控制序号与时间步
拒绝、ST 观察器占位拒绝、Host 回归、两份产品架构文档、任务表和操作记录。

## 2. 收口内容

- C 平台以 `foc_power_safety` 统一启动、提交、故障锁存和显式清故障事务；
- 目标启动改为 fail-closed：平台配置、初始化、ADC/PWM/保护绑定失败时不得开放输出；
- 快环使用同步 Vbus 输入，C 平台故障与 Rust `Fault` 状态形成粘滞传播；
- Rust bridge 拒绝失序 `control_sequence`、非法/漂移 `dt_s` 和未实现的 ST 观察器槽位；
- 增加独立 power-safety Host 测试并扩展平台、bridge、启动与观察器负例；
- `requirements-core.lock` 明确 PC 核心回归无第三方 Python 依赖，
  `requirements-hardware.lock` 单独锁定硬件工具依赖；
- 建立通用 FOC、双仿真、上位机以及 FOC-first 的统一执行路线；
- 修复构建哈希不可复现：`build.ps1` 默认设置 `SOURCE_DATE_EPOCH=0`，可用
  `-SourceDateEpoch <seconds>` 显式覆盖，并在退出时恢复原进程环境。

### 3.3 构建可重复性

收口检查发现 RT-Thread `kservice.c` 的版本输出使用 `__DATE__`/`__TIME__`，此前相同源码
每次完整重生成都会改变 BIN/HEX 哈希。加入固定 `SOURCE_DATE_EPOCH` 后，连续两次
Diagnostic `-Regenerate` 的 BIN 均为
`74CC6EE46BFCE1B126D85896BAB05578DE517B5887183C16279205F43862F082`，逐字节一致。
构建脚本还验证了退出后不会把该环境变量泄漏到调用者进程。

`SOURCE_DATE_EPOCH=0` 会让 RT-Thread 的编译日期显示为 Unix epoch；它是可重复构建标识，
不是实时时钟或固件烧录时间。发布流水线若需要另一个稳定日期，应显式传入固定秒值并将
该值与哈希一起记录，不能使用每次变化的当前时间。

## 4. 不能由本报告证明的内容

- 没有验证真实 TIM1/ADC/Break 中断竞争、首拍中性占空比或 driver fault 抢占；
- 没有执行 UV/OV、错误平台配置、过流、deadline 或观察器丢失注入；
- 没有进行 10,000 次安全事务耐久、trace-on 或闭环 WCET；
- 没有重新烧录当前构建产物，板上仍是此前实机复验过的 Diagnostic 镜像；
- Host、目标构建和 PC 仿真 PASS 都不是 S4～S6 的实机/产品证明。

这些缺口分别保留在 P0.2、P0.3、P0.4 和 P0.5，不因 P0.1 完成而自动关闭。
