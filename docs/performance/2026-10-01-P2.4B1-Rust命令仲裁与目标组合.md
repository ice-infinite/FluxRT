# P2.4B1 Rust 命令仲裁与目标组合检查点

## 1. 结论

外部控制公共层已经从 C fake sink 接到真实 Rust `CommandArbiter`，但仍保持默认关闭：

- 新增独立命令管理 ABI，支持1～8个固定来源、configure/submit/poll/status；
- 4 KiB调用者存储、无堆、无锁，只有单一管理线程可以拥有；
- C `foc_command_service`只能经`foc_command_rust_adapter`进入Rust仲裁器；
- STM32G431资源表明确保留TIM1、TIM2、ADC12、BEMF/电位器ADC和当前LPUART1控制台；
- feature-on目标镜像会初始化全关闭组合根，ABI/默认配置失败会阻止controller bind；
- 没有新增UART/CAN/PWM等物理能力，没有管理任务消费poll结果，更没有自动arm。

本阶段不实现持久化`ExternalIoConfig`。这不是遗漏：现有512 B记录的最大payload为468 B，
V2已使用340 B，只剩128 B；完整外部I/O配置为296 B，不能安全塞入。禁止截断或另存一份
失去原子性的旁路配置。

## 2. 代码边界

| 路径 | 职责 |
|---|---|
| `rust/crates/foc-rt-bridge/src/command_abi.rs` | 固定容量Rust仲裁ABI、错误映射、poll决定和计数 |
| `foc/include/foc_command_arbiter_bridge.h` | C/Rust定宽布局、4 KiB不透明上下文和函数契约 |
| `applications/foc_command_rust_adapter.c/.h` | 把command service的configure/submit函数表绑定到Rust ABI |
| `applications/foc_external_io_management.c/.h` | feature-on组合根；初始化board能力、Rust adapter和默认关闭command service |
| `foc/platform/stm32g431/foc_external_io_board.c/.h` | 板级资源占用事实；当前board capability仍为0 |
| `applications/main.c` | feature-on时做ABI自检、全关闭初始化和`FEXT`启动报告 |

Rust仲裁输出仍是`Safe`或`Selected(setpoint/action)`管理决定。它没有调用MotorService、
`foc_rust_start_realtime()`、TIM1或栅极；后续低频管理任务还必须再次检查Axis/fault/反馈/
功率条件，才能把决定交给状态机。

## 3. 配置容量决定

下一子阶段P2.4B2采用一个统一原子记录，不采用独立sidecar：

| 项 | 当前V2 | 规划V3 |
|---|---:|---:|
| 槽大小 | 512 B | 768 B |
| 现有payload | 340 B | 340 B |
| ExternalIoConfig canonical payload | 无 | 296 B |
| 合计payload | 340 B | 636 B |
| header + commit | 44 B | 44 B |
| 剩余 | 128 B payload空间 | 88 B总记录空间 |
| 配置C ABI上下文 | 2 KiB | 重新测量，预计提升到4 KiB |

V3迁移必须把V0/V1/V2的所有外部transport/input mask补为0；扩槽、配置ABI升级、双槽掉电
穷举和目标Flash布局必须同一检查点完成，不能只改结构大小。
