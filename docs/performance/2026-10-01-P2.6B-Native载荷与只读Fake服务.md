# P2.6B Native载荷与只读Fake服务

日期：2026-10-01
证据等级：S0契约 + S1 Rust/Python/C Host + S2 Cortex-M4F静态库/默认固件
硬件状态：未烧录、未连接物理transport、未运行电机

## 1. 结论

FluxRT Native已从“只有帧”推进到首批可互操作payload：Identity 48 B、Capabilities 64 B、
Status 64 B、CommandResult 32 B，以及ProductCommand 104 B逐字段映射。Rust `no_std`
仍是唯一编码/校验实现，C只使用固定ABI。

196 B Fake service可以完成完整request frame decode→只读处理→response frame encode；
Discover/Capabilities/Status可读，ProductCommand只返回`READ_ONLY`，参数写消息拒绝。它没有
RTOS任务、driver、CommandService/MotorService或PWM接点。

## 3. 安全与架构门

- payload未知mask/枚举、非有限浮点、非零reserved和capability子集冲突均拒绝；
- Status无valid位时对应物理量必须规范为零，禁止把旧值伪装成有效值；
- ProductCommand先逐字段解码，再调用产品契约校验；不会因为内存布局恰好一致而`memcpy`；
- Fake service不拥有命令sink，所有ProductCommand恒为错误响应且accepted sequence为零；
- 当前G431的`board_transport_mask`仍为0，Fake向量中的能力不是板级能力声明；
- Kconfig默认关闭，默认ELF中Native符号为0。

## 5. 负证据与修正

- 直接在普通PowerShell调用`cargo`失败，因为Rust工具链不在会话PATH；改用项目脚本同一
  `%USERPROFILE%\.cargo\bin\cargo.exe`，代码测试通过。
- 一次在仓库根目录执行未带`--manifest-path`的Cargo命令失败；随后在`rust/`目录重跑并
  通过Clippy。没有放宽检查门。
- 旧交接表沿用的默认BIN哈希与当前同尺寸产物不同；执行`-Clean`后重新`-Regenerate`
  得到稳定当前哈希`26FBE3EA...AC79`，并再次确认Native符号0。旧哈希只保留为历史快照。
