# FluxRT 可选外部控制与通信架构

## 1. 结论与当前边界

FluxRT 后续统一支持以下外部控制入口：

- UART / USB CDC；
- 经典 CAN / CAN-FD；
- FluxRT Native、DroneCAN、Cyphal/UDRAL、CANopen/CiA 402；
- PWM 脉宽输入、DShot、模拟量 ADC、Step/Dir；
- EtherCAT（独立硬件平台能力）。

P2.4C 已冻结第三方依赖硬规则：RT-Thread 未提供合适官方组件时，只能从协议所有者的官方
仓库或官方生成器获取，固定经过评审的精确 tag/commit，并隔离在 `third_party/`；FluxRT 只写
port 和 adapter。禁止重写第三方 wire codec/状态机、把官方源码复制进业务目录后魔改，或让
FOC 直接 include 上游头文件。无官方可复用实现时保持 feature 关闭并延期。详细上游候选、
升级流程和 PX4 路线见[第三方协议依赖与 PX4 接入策略](第三方协议依赖与PX4接入策略.md)。

所有入口采用“两级选择”：

1. **编译期选择**：Kconfig 决定驱动、协议和输入适配器是否进入固件，形成
   `compiled_capabilities`；
2. **运行期选择**：版本化配置决定已编译能力中哪些真正启用、如何映射、权限、优先级、
   lease、timeout 和失效动作。

仅编译某项能力不会启用控制，更不会 arm 功率级。运行期配置默认全部关闭；输入只有经过
解析、校验、命令仲裁和 MotorService 安全门后，才能成为 FOC 的参考值。

P2.4A 已把公共设备端骨架落实为代码：`foc_external_io.h/.c`提供固定布局 capability、
`ExternalIoConfig`、来源策略和资源冲突校验；`foc_transport_service`提供每实例有界SPSC
收发队列与健康统计；`foc_input_service`保存规范化输入、来源、sequence和timeout状态；
`foc_command_service`是adapter进入后续Rust `CommandArbiter`的唯一入口。总开关
`FOC_EXTERNAL_IO_FRAMEWORK`默认关闭，当前默认目标map中上述符号均为0。

P2.4B1已接入真实Rust arbiter sink和STM32G431资源事实表；P2.4B2把296 B外部I/O配置
纳入768 B V3统一记录，并增加唯一低频poll owner与308 B只读事件快照。P2.5A2再升级为
384 B External I/O V2和配置/管理ABI V4，加入88 B simple input标定；V3迁移保留transport/link
但关闭全部旧输入。配置变更归Management action。当前主循环已有10 ms management poll，
但真实Flash/RT-Thread配置服务尚未调用input owner启停事务，也没有MotorService执行回调。

P2.5A1/A2完成PWM pulse、Analog和Step/Dir的纯Rust归一化/映射、固定C ABI、setpoint-only
适配器、持久化标定和InputService→CommandService接线；P2.5A3又冻结公共raw-capture端口，
并实现默认关闭的PC2/ADC1_IN8 Analog候选。P2.5A4软件门已增加唯一management input owner，
把raw样本接入Rust归一化、InputService和CommandService，并覆盖timeout/越界/漏采/恢复与
ADC1 regular所有权；HW1在PC2占用ADC1时改由ADC2读取同一PA0 Vbus。HW2又在主电源断开
条件下完成PC2 raw、ADC2 fallback、资源归还和DWT时序板端门，并增加9 KiB runtime heap链接
保护。三项产品能力仍关闭，也没有MotorService执行。尚未实现UART/USB/CAN协议、DShot和EtherCAT平台，真实
Flash/RT-Thread配置服务也未接入。真正的FluxRT Studio不在当前
阶段开发，只保留设备协议边界，最后再实现上位机。

P2.5A2D又完成平台依赖收口：公共management只接受注入的capability，不包含
`foc_external_io_board.h`或调用STM32G431命名函数；`foc_external_io_platform.h`定义构建期
唯一provider，当前实现留在`foc/platform/stm32g431/`。Host管理测试和独立头文件编译均不
提供平台include/source，防止依赖倒灌。该结果不等于第二MCU已经移植完成。

P2.5A3/A4的资源核对确认：PC2是IHM16M1的`SPEED`/ADC1_IN8路径，可以作为Analog候选；PB4经
0 Ω电阻接作`CURRENT_REF`，不能作为安全的TIM3/PWM输入。PWM pulse与Step/Dir必须重新选择
专用连接器引脚。Analog候选只在上一拍EOC有效时读取DR并启动下一拍转换，不在ISR轮询；
PC2 driver启用时旧HAL regular监控不再碰ADC1，stop也必须等待ADSTART清除。HW1已选择独立
安全采样路径：fault-clear所需Vbus从同一`PA0/ADC12_IN1`经ADC2读取，停机清除旧同步样本有效位。
HW2无功率S4已证明raw采集无漏样、fallback生效、最终owner归还且monitor ISR最坏1064 cycles；
但只观察了PC2中点附近和断电Vbus近零，未施加已知多点电压。产品`board_input_mask`仍保持0，
必须先通过HW3端点/断线/恢复迟滞和正式配置事务，才允许开放Analog。

## 2. 不可绕过的数据主线

```text
UART / USB / CAN / EtherCAT / PWM pulse / DShot / ADC / Step-Dir
                              │
                              v
                   C Platform Transport/Input Driver
             raw bytes / CAN frame / pulse / count + timestamp
                              │
                              v
                  Protocol or Input Adapter (bounded)
           decode → normalize SI → validate → ProductCommand
                              │
                              v
              bounded mailbox → CommandArbiter (Rust no_std)
        source / sequence / permission / priority / lease / timeout
                              │
                              v
                MotorService / Axis state and safety gates
                              │
                              v
              Torque / Velocity / Position reference snapshot
                              │
                              v
                        FOC realtime owner
```

禁止路径：

- 通信中断、CAN 收包回调或 PWM 输入捕获直接写 TIM CCR；
- 协议解析器直接修改 Rust controller context；
- 外部 setpoint 自动等价于 arm；
- 通信恢复后自动复活超时前的旧命令；
- 把主机时间直接当作设备单调时钟；
- 通过运行期配置启用没有编译或没有板级 capability 的能力。

## 3. 三种状态必须分开

每个 transport、protocol 和 input adapter 都有三个不同状态：

| 状态 | 含义 | 来源 |
|---|---|---|
| `compiled` | 代码和驱动存在于当前镜像 | Kconfig、链接 map、固件 capabilities |
| `configured_enabled` | 停机事务批准该能力可接收输入 | 持久化配置 active revision |
| `healthy/active` | 接口在线且其命令当前赢得仲裁 | 运行时状态、watchdog、CommandArbiter |

`compiled=true` 不推出 `enabled=true`，`enabled=true` 也不推出当前拥有 Axis。上位机必须同时
显示三者，不能只显示一个“已连接”。

## 4. 编译期选择

P2.4A先增加一个**有真实实现**的公共骨架总开关：

```text
FOC_EXTERNAL_IO_FRAMEWORK    default n
```

它编入契约、校验器和三个服务，但不会宣称任何物理接口。P2.5A1现已加入三个具有纯逻辑、
ABI、adapter和测试的输入开关，仍不代表物理驱动存在。其余开关按P2.6～P2.8逐项加入；
没有对应实现和测试时不得提前建立空开关：

```text
FLUXRT_TRANSPORT_UART
FLUXRT_TRANSPORT_USB_CDC
FLUXRT_TRANSPORT_CAN_CLASSIC
FLUXRT_TRANSPORT_CAN_FD
FLUXRT_TRANSPORT_ETHERCAT

FLUXRT_PROTOCOL_NATIVE
FLUXRT_PROTOCOL_DRONECAN
FLUXRT_PROTOCOL_CYPHAL
FLUXRT_PROTOCOL_MAVLINK_MANAGEMENT
FLUXRT_PROTOCOL_CANOPEN_CIA402
FLUXRT_PROTOCOL_ETHERCAT_COE_CIA402

FLUXRT_INPUT_PWM_PULSE
FLUXRT_INPUT_ANALOG
FLUXRT_INPUT_STEP_DIR

# FLUXRT_INPUT_DSHOT尚不存在；通过官方上游选择门后才允许加入
```

依赖规则：

- DroneCAN、Cyphal、CANopen 至少依赖一种 CAN transport；
- MAVLink management 依赖 UART/USB/CAN 中经过批准的管理 transport，不取得实时 Axis owner；
- CAN-FD 还依赖 MCU 控制器、收发器和板级布线 capability；
- EtherCAT CoE 依赖 EtherCAT transport 和明确的 ESC/DC 同步能力；
- PWM、DShot、Step/Dir 依赖互不冲突的 timer/channel/pin；
- Analog input 依赖不与相电流、母线和相电压采样冲突的 ADC channel；
- 某块板不具备的能力不能通过 Kconfig 强行声明；配置和目标启动自检都要再次复核。

所有新能力初次合入均 `default n`。Production 可以在产品配置明确选中后编入已验证能力，
但运行时仍默认关闭；Diagnostic 负责候选验证，不能把 Diagnostic 开关残留自动带入
Production。

## 5. 运行期配置

旧配置 schema V2 中的 `AppConfig` 只有：

```text
version / can_node_id / uart_baud / command_source_count / command_sources[4]
```

它不足以表达多transport、多协议和输入标定。P2.4A建立了独立配置和
`foc_external_io_validate_config()`；P2.5A2已把配置升级为V2/384 B，并将PWM、Analog和
Step/Dir的88 B版本化标定组写入V4 768 B双槽模型，接入
candidate→validate→apply→commit/rollback事务，而不是继续向旧`AppConfig`塞字段或建立
非原子sidecar。V0～V2迁移生成全关闭External I/O组；V3保留transport/link但关闭全部
simple input。目标真实Flash服务和对外参数协议仍未接入。V4 payload已恰好占满724 B，后续
扩展必须先调整存储布局。
公共结构表达：

```text
struct ExternalIoConfig {
    version;
    transport_enable_mask;
    input_enable_mask;
    uart_config;
    usb_config;
    can_config;
    pwm_input_config;
    dshot_config;
    analog_input_config;
    step_dir_config;
    ethercat_config;
}
```

所有配置通过现有 `candidate → validate → apply → commit/rollback` 事务；只允许 Disabled 状态
修改会影响通信控制权、引脚、timer、DMA、节点 ID、映射或 timeout 的字段。

### 5.1 CAN 选择

CAN 配置把物理链路和上层协议分开：

```text
link_mode: Disabled / Classic / FD
protocol:  FluxRtNative / DroneCan / Cyphal / CanOpenCia402
node_id
nominal_bitrate
data_bitrate
command_source_id
heartbeat_ms
command_timeout_ms
```

第一版同一个 CAN 控制器只允许一个控制协议，避免不同协议对相同 ID 或同一控制权产生歧义。
未来如需多协议共存，必须先冻结互不重叠的 ID/filter 规划、独立来源身份和总线预算，不能只
打开两个 parser。

### 5.2 简单外部输入

PWM、DShot、Analog 和 Step/Dir 都应映射为统一 `ProductCommand`，但各自保留物理配置。
P2.5A1实现PWM/Analog/Step-Dir的纯换算和setpoint-only适配；P2.5A2又完成持久化标定、
配置迁移和Input/Command service接线；P2.5A3实现PC2 Analog原始采集候选；P2.5A4/HW1软件门
补齐生命周期owner、失效/恢复和ADC2安全Vbus路径，但仍不启动、不开放board capability。下表剩余物理通道与
硬件验收由P2.5A4-HW及后续专用引脚批次完成：

| 输入 | 必要配置 | 默认失效动作 |
|---|---|---|
| PWM pulse | 已持久化min/neutral/max、deadband、正负SI限值；PB4被CURRENT_REF占用，需另选引脚/Timer | timeout → Release/受控停机 |
| DShot | 速率、telemetry、命令范围、CRC错误门 | 连续坏帧/timeout → Release |
| Analog | PC2/ADC1_IN8 raw、ADC1唯一owner、timeout/越界/漏采/恢复及ADC2同源Vbus fallback已实现；ADC一致性、滤波/断线电气判据、WCET和无功率门待A4-HW | 越界/断线 → Release；ControlledStop在MotorService前显式降级为Release |
| Step/Dir | 已持久化steps/rev、microsteps、gear、方向、零位、最大频率；专用物理通道未定 | 无脉冲timeout → hold或stop，必须显式选择 |

每个输入还必须指定 `source_id`、权限、优先级、lease 和 timeout。物理值映射到 Torque、
Velocity 或 Position 时使用 SI 单位，并受 Axis 软限位、电流/转矩/速度限制再次约束。

默认策略只提交 setpoint，不自动提交 `ClosedLoopControl`。若产品确实需要“一路 PWM 信号即可
启动”，必须增加独立 enable/arming 条件、有效边沿和失效状态机，并作为单独安全能力验收。

### 5.3 EtherCAT

EtherCAT 不是普通串口 parser。STM32G431 当前板没有 EtherCAT Slave Controller，规划为
独立硬件能力：

- 外接 ESC（SPI/并口）或更换带 EtherCAT 从站能力的平台；
- 独立实现 ESC IRQ、mailbox、PDO、状态机和 watchdog；
- 可选 CoE/CiA 402 映射，但 Axis 状态仍由 FluxRT MotorService 最终裁决；
- Distributed Clocks 只提供同步事件时基，必须实测它到采样、控制拍和 setpoint 生效边界的
  延迟与抖动；
- EtherCAT OP 状态、PDO 新鲜度和 watchdog 超时均映射成来源健康与命令 timeout；
- 不允许 EtherCAT 栈直接持有 FOC controller 或写 PWM。

因此 EtherCAT 是 P2.8 和后续 U10 板卡适配任务，不计入当前 G431 板的默认 capability。

## 6. 协议与 transport 的职责

| 层 | 负责 | 不负责 |
|---|---|---|
| Platform driver（C） | 外设、IRQ/DMA、frame/pulse/count、硬件时间戳、bus-off/overrun | 控制模式、FOC、来源优先级 |
| Transport service（C/RT-Thread） | 固定容量队列、线程唤醒、发送调度、统计 | 解析后直接改控制器 |
| Protocol/Input adapter（优先Rust no_std） | 有界解析、CRC、单位归一、生成`ProductCommand` | arm、PWM寄存器、Flash |
| CommandArbiter（Rust） | 来源权限、sequence、时间、lease、timeout、抢占 | 底层硬件是否安全 |
| MotorService（管理层） | 状态迁移、配置/fault/feedback/母线复核 | 传输细节 |
| FOC realtime | 消费单一已批准参考快照 | 收包、字符串、动态内存 |

DroneCAN、Cyphal、MAVLink、CANopen 和 EtherCAT 等第三方栈只能来自官方上游，并以独立库
保留在 `third_party/`。C/适配层只提供栈要求的 transport port，以及官方消息与固定布局
命令/状态快照之间的转换。第三方栈不能跨入产品控制域、持有 controller 或绕过
CommandArbiter/MotorService。

## 7. 并发、资源和安全规则

- ISR 只采集并放入固定容量 ring/mailbox；解析和仲裁不在 ADC/FOC ISR 中执行；
- 每个队列定义容量、满队列策略、drop counter 和最高处理预算；
- 控制命令不得“丢旧留新”而不更新 sequence/drop 证据；
- 硬件 Break/driver fault 永远高于任何网络 EStop；网络 EStop 只能增加安全路径；
- 所有 transport timeout 使用设备单调时钟并正确处理 32 位回绕；
- bus-off、EtherCAT watchdog、UART framing error、PWM失脉冲和ADC越界都必须显式进入健康状态；
- 多来源可以同时启用，但同一时刻只有 CommandArbiter 选出的 owner 能控制 Axis；
- 配置变更、协议切换、bitrate、node ID 和 pin/timer 映射只在 Disabled 状态应用；
- 外部通信负载必须纳入线程、ISR、总线占用和完整 FOC deadline 测量。

## 8. 能力与遥测

设备 discovery/status 至少公开：

```text
compiled_transport_mask
compiled_protocol_mask
compiled_input_mask
configured_transport_mask
configured_input_mask
healthy_source_mask
active_source_id
active_protocol
lease_remaining_ms
last_sequence
rx_frames / tx_frames / crc_errors / parse_errors
dropped / overflow / timeout / bus_off / watchdog
```

FluxRT Studio 根据 compiled + configured capabilities 决定显示哪些页面；不能让 GUI 的选项
反向定义固件能力。

## 11. 分级验收

每种接口分别通过，不能用CAN通过代替PWM或EtherCAT：

1. **S1**：codec/adapter/arbiter单测、golden、fuzz、timeout和回绕；
2. **S2**：启用/关闭组合构建、size/map、无未引用伪能力、默认关闭；
3. **S3**：Rust PC + MATLAB/协议仿真注入延迟、丢包、乱序、抖动；
4. **S4**：无功率板端收发、timer捕获、bus-off/watchdog和完整ISR/线程WCET；
5. **S5**：限流、空载、短时受控实机；
6. **S6**：长测、多来源抢占、断线恢复、EMI/总线故障和独立时序真值。

任何阶段失败都只关闭对应 transport/protocol/input feature，不改变基本 FOC 默认路径。

## 12. 为未来 FluxRT Studio 和第三方工具保留的设备接口

本节只冻结边界和未来字段语义，当前不创建`host/fluxrt-studio/`、Host SDK、GUI页面或真实
管理连接。设备通信与控制入口先完成；P2.9再实现这些设备端操作，P7.1最后消费它们。

### 12.1 管理链路与控制链路分离

上位机连接设备的链路不一定等于当前控制来源。例如：

- Studio 通过 USB Native 协议配置设备，电机目标来自 DroneCAN；
- Studio 通过 UART 只读监控，Axis 当前由 PWM pulse 控制；
- EtherCAT 主站提供周期目标，Studio 通过 USB 读取 trace；
- Studio 通过 USB-CAN 使用 FluxRT Native 管理多个节点。

因此设备必须分别报告：

```text
management_transport
configured_control_inputs[]
healthy_control_inputs[]
active_source_id
active_protocol
```

Studio 切换连接方式不能自动改变 Axis owner；连接、获得管理会话和获得控制租约是三个独立
动作。

### 12.2 公共主机模型

设备协议和 Host SDK 预留以下稳定语义模型，具体消息编号在P1.4冻结：

| 模型 | 内容 |
|---|---|
| `ExternalIoCapabilities` | compiled transport/protocol/input mask、板级能力、可用实例和资源标识 |
| `ExternalIoConfigSnapshot` | active/saved revision、enable mask、协议、映射和timeout |
| `ExternalIoStatusSnapshot` | configured/healthy/active状态、当前协议、source和watchdog |
| `CommandSourceStatus` | source ID、权限、priority、owner、lease、last sequence和超时原因 |
| `TransportStatistics` | RX/TX、CRC/parse/drop/overflow、bus-off、watchdog、抖动和队列峰值 |
| `ResourceConflict` | pin/timer/ADC/DMA冲突、冲突对象和设备端拒绝原因 |
| `InputMonitorSample` | 原始pulse/count/ADC、规范化SI值、valid/quality和时间戳；只读 |

这些模型使用版本化schema，不暴露C结构体内存布局。未知字段按协议兼容规则跳过或拒绝，未知
枚举不能猜测回退。

### 12.3 设备协议操作面

在现有Discovery/Config/Telemetry/Control消息域中预留以下操作语义：

```text
READ_EXTERNAL_IO_CAPABILITIES
READ_EXTERNAL_IO_CONFIG
READ_EXTERNAL_IO_STATUS
READ_COMMAND_SOURCE_STATUS
READ_TRANSPORT_STATISTICS
SUBSCRIBE_EXTERNAL_IO_STATUS
SUBSCRIBE_INPUT_MONITOR
UNSUBSCRIBE_INPUT_MONITOR

BEGIN_CONFIG_TRANSACTION
SET_EXTERNAL_IO_CONFIG
VALIDATE_CONFIG_TRANSACTION
APPLY_CONFIG_VOLATILE
ROLLBACK_CONFIG_TRANSACTION
COMMIT_CONFIG_TRANSACTION
```

不再为每种接口发明一套保存流程。CAN、PWM、DroneCAN和EtherCAT配置都复用同一个配置事务，
设备返回字段级错误、资源冲突和所需AxisState。运行中只能读取状态和统计；会改变协议、pin、
timer、ADC、DMA、node ID、bitrate、映射或控制权的配置第一版必须Disabled。

`InputMonitorSample`仅用于观察输入质量，不会自动转换成Studio控制命令，也不能触发arm。

### 12.4 Host SDK 接口

FluxRT Studio 不直接拼帧，统一调用语言无关语义的客户端接口。Python首版建议：

```text
DeviceClient.connect(transport)
DeviceClient.read_identity()
DeviceClient.read_capabilities()
DeviceClient.read_external_io_capabilities()
DeviceClient.read_external_io_config()
DeviceClient.read_external_io_status()
DeviceClient.subscribe_external_io_status(...)
DeviceClient.subscribe_input_monitor(instance, ...)

ConfigSession.begin(base_revision)
ConfigSession.set_external_io(draft)
ConfigSession.validate()
ConfigSession.apply_volatile()
ConfigSession.rollback()
ConfigSession.commit()

ControlSession.acquire(source_id, requested_lease)
ControlSession.keepalive()
ControlSession.release()
```

未来C++/Rust/C# SDK复用同一schema和golden vectors，不复用Python实现细节。

### 12.5 Studio 分层和页面

在既有FluxRT Studio分层中新增：

```text
QML
  ExternalIoPage
  CommandSourcesPage
  BusDiagnosticsPage

Controllers
  ExternalIoController
  CommandSourceController

Services
  ExternalIoService
  CommandSourceService
  TransportRegistry

Adapters
  SerialTransport / CanTransport / EthercatManagementTransport
  ReplayTransport / FakeDeviceTransport
```

`ExternalIoPage`至少显示：

- 编译支持、配置启用、当前健康三列状态；
- 物理实例、pin/timer/ADC/DMA资源和冲突；
- 当前协议、node ID、bitrate、timeout和来源策略；
- 原始输入与SI映射预览；
- active owner、lease和最近一次切换原因；
- frame/drop/CRC/bus-off/watchdog统计；
- active/saved/draft差异以及Validate/Apply/Rollback/Commit状态。

页面根据设备capability动态显示，但隐藏页面不等于关闭设备功能。任何启停都必须形成明确配置
diff并经过设备事务。

### 12.6 FakeDevice、Replay和兼容矩阵

上位机代码开始前先准备以下FakeDevice profile：

1. 只有UART Native；
2. CAN Classic + FluxRT Native；
3. CAN-FD + DroneCAN；
4. PWM + Analog双来源，模拟抢占和timeout；
5. 编译支持EtherCAT但硬件/配置未启用；
6. EtherCAT OP运行、watchdog丢失；
7. pin/timer/ADC资源冲突导致Validate拒绝；
8. 新固件/旧Studio和旧固件/新Studio兼容负例。

Replay文件必须保存identity、capabilities、配置revision、schema、设备时间和transport统计，避免
离线页面把缺失字段误显示为有效零值。

### 12.7 上位机实施门

| 阶段 | 外部I/O交付物 | 权限边界 |
|---|---|---|
| Studio S0 | schema、Host模型、FakeDevice capability矩阵、golden vectors | 无真实设备写入 |
| Studio S1 | capability/status/source/statistics只读页 | 不启用接口、不arm |
| Studio S2 | `ExternalIoConfig` draft/validate/apply/rollback/commit | 仅Disabled配置事务 |
| Studio S3 | 输入质量监视、控制租约与timeout可视化 | setpoint与arm仍是独立请求 |
| Studio S5 | Replay、Rust/MATLAB/实机通信故障对比 | 仿真不能批准硬件能力 |
| Studio S6 | CAN多节点、协议映射、升级；EtherCAT管理页按硬件能力加入 | 每种协议独立验收 |

设备侧对应P2.9“未来上位机的设备接口”，在P2.5～P2.8通信/输入能力稳定后实现schema、消息、
golden vectors和Fake client，不开发GUI。真正的Host SDK与Studio页面归P7.1，放在产品功能和
通信主体之后；它不能提前于设备schema自行创造字段。
