## 1. 执行摘要

本次从工程入口、启动顺序、C/Rust 所有权、ADC 快环、Break 关断、保护配置、
观察器状态机、FFI、测试体系、构建与文档一致性逐层审计。现有全套回归和四种目标
构建档均通过，但源码中仍确认 **17 项问题或工程缺口**：

| 严重度 | 数量 | 含义 |
|---|---:|---|
| P0 / Critical | 1 | 存在可导致非预期输出开放的中断竞争，修复前不应继续带功率级运行 |
| P1 / High | 5 | 保护、故障锁存、初始化或验证门存在高风险缺口 |
| P2 / Medium | 7 | 会造成误停、错误诊断、接口契约失真或显著增加后续缺陷概率 |
| P3 / Low | 4 | 可复现性、可维护性、文档和操作可读性问题 |

最重要的结论如下：

1. `foc_platform_control_start()` 与已运行的 ADC ISR、最高优先级 Break ISR 之间没有
   原子启动事务。`g_foc_control_armed` 在 CCER/MOE/栅极使能之前发布，ADC 可在这段
   窗口中计算并写入非中性 CCR；线程恢复后会把这个 CCR 直接接到功率级。Break 在
   启动窗口内抢占后，启动线程也可能继续开放输出。该问题定为 **P0**。
2. 普通 Diagnostic/Production 快环不在每个控制拍同步采集 Vbus。运行中使用的是 arm
   前缓存值，欠压、回馈过压和模型电压误差都无法被可靠发现。
3. C 平台故障和 Rust `Fault` 状态没有形成统一、锁存的故障事务。普通启动会自动清除
   deadline/control/output-rejected 等位，且 C 没有调用已有的 `foc_rust_latch_fault()`；
   用户可以在没有显式故障清除和重新自检的情况下再次启动。
4. 平台配置只检查“数值形式合法”，没有板级不可放宽的硬上限。Shell 可把软件过流
   阈值设置到 ADC 永远达不到的范围，违背现有架构文档“上层只能收紧”的约束。
5. 当前 Host C 测试没有编译 `FOC_TARGET_STM32G431`，因而 P0 涉及的寄存器、中断和
   实际 arm 路径全部没有被执行。测试全绿不能覆盖这些问题。

建议在修复 `FRT-001`～`FRT-006` 并完成目标板故障注入前，保持电机和功率输出关闭；
至少不要继续闭环、长时间或高功率试验。

## 3. 当前架构与真实调用链

### 3.1 初始化顺序

```text
main_thread_entry
  -> foc_rust_init
  -> 生产参数/运行配置装配
  -> foc_rust_configure
  -> foc_platform_configure
  -> foc_platform_init
       -> GPIO/TIM1/ADC/Break/DWT
       -> ADC offset calibration
       -> 同步采样时基启动（ADC IRQ 已启用）
  -> 频率一致性检查
  -> foc_platform_bind_controller
  -> 等待 100 ms / 首次反馈 / FBOOT
```

`foc_platform_configure()`、`foc_platform_init()`、`foc_platform_bind_controller()`
按设计应组成 fail-closed 链，但当前 bind 条件漏掉了第一步，见 `FRT-005`。

### 3.2 普通运行路径

```text
Shell foc_start
  -> foc_platform_control_start
       -> 非实时 Vbus/故障检查
       -> foc_rust_start_realtime (进入 Alignment)
       -> 写 50% CCR + UG
       -> 发布 armed
       -> 开 CCER / MOE / 外部 gate enable

ADC1_2_IRQHandler @ 12 kHz
  -> 读取双 ADC 注入电流并重构第三相
  -> 软件过流 / driver fault / controller bound 检查
  -> foc_realtime_input_from_legacy
  -> foc_rust_realtime_step
       -> V19 校验
       -> 观察器 / 启动状态机 / 电流环 / 速度环 / SVPWM
  -> C 二次 duty 窗口检查
  -> TIM1 CCR1/2/3 commit
  -> deadline 统计，超限则关断
```

### 3.3 故障与停止路径

- Break IRQ 优先级 0，可抢占优先级 1 的 ADC ISR；
- Break、软件过流、driver fault、Rust 返回错误、输出拒绝和 deadline 超限都会调用
  `foc_platform_disable_power_fast()`；
- 普通 `foc_stop` 还会调用 `foc_rust_stop()`；
- 但是 ISR 故障路径没有统一进入 Rust `Fault`，普通重新启动还会清部分平台故障位，
  因而目前不存在单一、可证明的故障锁存状态机。

### 3.4 所有权判断

现有设计方向基本正确：平台层拥有 ADC、PWM、Break 和板级标定；Rust 拥有控制算法和
逻辑状态；ADC ISR 是 arm 后 Rust 可变控制器状态的唯一调用者。但“启动/停止/故障清除”
跨越线程、ADC ISR、Break ISR 和 Rust 状态，尚未被实现成同一个事务，这正是最高风险
问题的共同根因。

## 5. 详细发现与修复方案

### FRT-001｜P0｜arm 事务与 ADC/Break 中断竞争

**证据**

- `foc/platform/stm32g431/foc_platform_stm32g431.c:1390-1393`：ADC IRQ 优先级 1，
  Break IRQ 优先级 0，且两者在启动前已经使能；
- 同文件 `1362-1413`：同步 TIM1/ADC 时基在普通 arm 之前运行；
- 同文件 `2736-2748`：先写 50% CCR 和 UG，然后清 Break 标志，随后在 CCER、MOE、
  外部栅极使能之前写 `g_foc_control_armed = 1U`；
- ADC ISR 在 `2233` 读取 armed，在 `2355-2357` 直接提交 Rust 输出的 CCR；
- Break ISR 在 `2454-2482` 锁存标志、关断输出并停止 TIM1，但 arm 后续代码没有检查
  fault epoch，也没有把整个序列作为事务取消；
- Ls(I) 首次输出开放在 `773-808` 重复了同一模式：清 Break、发布 armed、开放输出，
  后置检查不验证 Break latch 或 session permit。

**可触发的交错**

```text
线程：写入中性 CCR -> g_foc_control_armed = 1
ADC ：抢占 -> 看见 armed -> Rust 计算 -> 写入非中性 CCR -> 返回
线程：CCER/MOE/gate enable -> 第一个实际输出不是承诺的中性占空比
```

另一个窗口是 Break 在 arm 中间抢占：Break 关断并锁存后，线程恢复仍可能继续写 CCER、
MOE 和 gate enable。若 driver fault 引脚已经恢复，现有后置检查不能识别这次瞬态故障。

**影响**

- 违反“中性 CCR 已经稳定后才开放功率级”的启动不变量；
- 启动首拍可能产生不可预测转矩；
- 瞬态 Break 可能被启动路径的清标志和继续执行掩盖；
- 与 `FRT-003` 组合后，可在没有显式故障恢复事务的情况下重新开放输出。

**根因**

arm 被实现成一组普通寄存器写入，而不是带 permit、故障纪元、提交点和回滚的状态事务；
`g_foc_control_armed` 同时承担“允许 ADC 计算”和“物理输出已经开放”两个不同含义。

**修复方案**

1. 引入明确状态：`DISABLED -> ARMING -> ARMED -> FAULT_LATCHED`；ADC 只在 `ARMED`
   运行控制，不把 `ARMING` 当作授权；
2. 将 Break、driver fault、软件过流、deadline 等统一更新单调递增的 `fault_epoch` 和
   锁存位；启动保存 epoch，提交前必须仍相等；
3. 在目标芯片上使用经验证的临界区，只屏蔽 ADC/普通中断，保持硬件 Break 链有效；
   严格按 TIM1 Break 语义设计 BIF/MOE 清除顺序，不能由通用 start 无条件清 BIF；
4. 先预装载中性 CCR，再检查 Break 锁存、driver pin、同步状态、permit 和 epoch，最后
   以单一提交函数开放 CCER/MOE/gate；提交失败统一回滚到 `FAULT_LATCHED`；
5. Ls(I) 首次输出调用相同提交函数，并额外要求 active session token 未撤销；
6. 变量拆分为 `control_execute_permit` 与 `power_stage_active`，禁止用一个 armed 位表达
   两种时序状态。

**验收**

- 在 arm 的每个寄存器写入边界注入 ADC 和 Break，所有排列都必须得到“中性首拍”或
  “保持关断”，不得得到非中性首拍；
- 示波器同时观察 gate enable、三相 PWM、Break 输入和 ADC 触发；
- 目标板至少连续执行 10,000 次 arm/stop 故障注入，无窄脉冲、无非中性首拍；
- 普通 arm 和 Ls(I) arm 共享同一组事务测试。

### FRT-002｜P1｜普通运行路径没有实时 Vbus

**证据**

- `foc_platform_sample_monitor_inputs()` 在平台文件 `1216-1243` 更新
  `g_foc_diagnostics.bus_voltage_raw`；
- 它只在初始化 `1454` 和 `foc_platform_read_feedback()` 的未 arm 分支 `2525` 调用；
- ADC ISR 在 `2284-2286` 每拍把这个缓存值转换后交给 Rust；
- 普通 start 只在 `2700-2706` 做一次母线窗口检查；
- Identification 的 Ls(I) 路径在 `2090-2100` 已经有同步 `ADC1->JDR2` Vbus，但普通
  Diagnostic/Production 路径没有等价采样。

**影响**

- 运行中电源跌落、断电或再生导致的过压不会被软件保护及时发现；
- SVPWM 电压归一化和观察器命令电压模型持续使用旧母线值；
- 心跳看似报告 Vbus，实际可能是启动前缓存，容易产生错误安全判断。

**修复方案**

- 把 Vbus 纳入普通快环的同步注入组或确定性 DMA 通道；
- 输入结构增加 `vbus_sequence`、`vbus_age_ticks`、valid 位和量程/饱和错误；
- 平台层实现带迟滞和去抖的运行时 UV/OV 锁存，先硬关断，再向 Rust 映射故障；
- 控制律只消费通过 age/valid/range 校验的 Vbus；无效或过旧必须 fail closed；
- 重新测量 ADC ISR WCET、采样窗和相电流串扰，不能只以交叉构建通过为验收。

### FRT-003｜P1｜平台故障与 Rust Fault 状态分裂

**证据**

- V19 已定义 `hardware_fault_flags`，Rust 在 `foc-rt-bridge/src/lib.rs:2674-2679`
  消费它；但目标 ISR 使用的 legacy 包装在 `foc/include/foc_rust_bridge.h:739` 把硬件
  故障固定为 0；
- Rust 已提供 `foc_rust_latch_fault()`（`3686-3696`），头文件也要求平台故障调用它，
  但目标 C 运行路径没有调用；
- 软件过流/driver fault、Break、deadline、Rust 错误和输出拒绝主要只调用
  `foc_platform_disable_power_fast()`；
- `FOC_TRIAL_FORBIDDEN_FLAGS`（平台文件 `279-285`）没有包含 deadline、control error、
  output rejected；
- `foc_platform_control_start()` 在 `2732-2735` 自动清除这些位；
- `foc_rust_start_realtime()`（Rust `2568-2614`）只拒绝 `Fault`，并不要求当前状态必须
  是 `Disabled`。

**影响**

一次 deadline missed、C 二次输出拒绝或硬件关断后，C 和 Rust 对系统状态的判断可能
不同。操作者执行新的 `foc_start` 会清掉部分平台证据并复位控制器，而不是经过明确的
故障恢复、自检和授权流程。这违反架构文档“故障锁存并阻止 re-arm”的约束。

**修复方案**

- 建立唯一 `foc_fault_latch(reason)`：第一步硬关断，第二步原子锁存平台位和 epoch，
  第三步在安全上下文把映射后的故障写入 Rust；
- 普通 arm 的 forbidden 集合包含所有安全相关位，start 永不清故障；
- 只允许独立 `foc_fault_clear` 清除，且必须同时满足：物理输出关闭、硬件条件恢复、
  Vbus 合法、ADC/offset/sync 自检通过、Rust 回到 Disabled；
- `foc_rust_start_realtime()` 只接受 `Disabled`，其它状态返回明确错误；
- 保留 first-fault reason、last-fault reason 和计数器，清除锁存不清历史证据。

### FRT-004｜P1｜上层可放宽板级保护阈值

**证据**

- 默认值是 Vbus 7～18 V、软件过流 1.15 A、duty 3%～97%、deadline 12750 cycles
  （平台文件 `55-83`）；
- `foc_platform_configure()`（`1853-1875`）只检查正数、大小关系和 duty 位于 0～1，
  没有对板级批准值做上限/下限约束；
- Shell 的 `foc_cfg trip`（`applications/main.c:1325-1344`）可直接提交任意正数；
- `foc_platform_current_trip_counts()` 最终钳到 32767，而实际重构 ADC 差值远小于该值，
  因而足够大的阈值会使软件过流门事实上不可达；
- [整改架构与职责分配](整改架构与职责分配.md) 明确要求 C 平台拥有不可放宽的
  `ProtectionConfig`，上层只能请求更保守的值。

**修复方案**

- 拆成编译期/板级 `hard_limits` 与运行时 `requested_limits`；有效值只能取更保守一侧；
- 平台校验明确限制：过流不得高于经批准的板级值，Vbus 窗口不得扩大，duty 不得超出
  3%～97%，deadline 必须小于物理周期且不大于经实测批准值；
- Shell 修改保护参数要求输出关闭，并打印 requested/effective/hard 三组值；
- 加边界测试：每个批准值的等值、刚低于、刚高于、NaN/Inf、极大值；必须包含
  `foc_cfg trip 100000` 的拒绝用例。

### FRT-005｜P1｜平台配置失败不会阻止绑定

**证据**

`applications/main.c:1468-1492` 的注释声称 configure/init/bind 任一失败都禁止 arm，
但实际代码始终调用 `foc_platform_init()`，bind 条件只检查 `platform_status` 和
`rust_status`，没有检查 `platform_config_status`。

当前编译期默认配置合法，所以正常构建不触发；但只要未来参数装配、版本迁移或内存
破坏让 configure 拒绝，平台仍会保留内部旧默认值并完成 init/bind，形成 fail-open。

**修复方案**

- `configure != OK` 时立即 emergency stop，跳过 init 和 bind；
- 用单一 `boot_gate_status` 聚合所有步骤，只有全 OK 才允许 bind；
- FBOOT 报告每一步状态，但不得用报告代替控制流门；
- 添加故意非法平台配置的启动测试，断言 controller 未绑定、start 拒绝、输出寄存器
  保持安全。

### FRT-006｜P1｜现有测试没有执行真实目标 arm/IRQ 路径

**证据**

- `test.ps1:13-18` 明确声明 C 侧只验证空状态拒绝和同拍时序；
- `tests/host/CMakeLists.txt` 会编译平台文件，但未定义 `FOC_TARGET_STM32G431`，所以
  寄存器、NVIC、ADC ISR、Break ISR 和真实 arm 代码均被预处理排除；
- `test_foc_motor_arm_gate.c` 只验证 Calibration/Identification 的编译期拒绝，不覆盖
  Diagnostic/Production 输出开放；
- 本次所有现有测试通过，但没有任何一个测试能构造 `FRT-001` 的中断交错。

**修复方案**

1. 抽出纯 C 的 `ArmTransaction` 和 `OutputCommit` 状态机，使用寄存器适配接口；
2. 为 STM32 寄存器做 fake CMSIS/寄存器模型，Host 测试编译真实 target 分支；
3. 在 arm、Rust step、CCR commit 的每个 hook 注入 Break/ADC/driver fault；
4. 增加 HIL：真实 Break 引脚、软件过流、Vbus UV/OV、ADC stale、deadline 和串口重试；
5. 将“故障后必须显式 clear 才能 re-arm”写成跨 C/Rust 的端到端测试。

### FRT-007｜P2｜Break 后 ADC 可写回非零 CCR

ADC ISR 在调用 Rust 后，到 `2355-2357` 写 CCR 前没有再次检查 armed、Break latch、
driver fault 或 fault epoch。Break 优先级更高，可在 Rust 计算期间抢占并把 CCR 清零、
关 gate、停定时器；ADC 恢复后仍会把刚算出的非零 CCR 写回。

由于 gate/MOE 已关，这个问题单独看通常不会立即上电，但破坏了“故障后寄存器也保持
安全值”的后置条件，并会放大错误 re-arm 的风险。

**修复**：所有输出写入经唯一 `commit_output(expected_epoch, output)`；Rust 计算前后
比较 epoch，提交前再验证 ARMED、无 latch、driver pin、同步时基；失败时写安全 CCR，
不增加成功 step 计数。用 Break 抢占 Rust 计算和三次 CCR 写入边界的测试验收。

### FRT-008｜P2｜观察器获取超时误覆盖过渡阶段

Rust 注释和字段说明都说 `observer_wait_elapsed_s` 只在 `OpenLoopHold` 累加，但
`foc-rt-bridge/src/lib.rs:2984-2988` 实际匹配
`OpenLoopHold | ObserverTransition`。如果观察器在超时前一拍刚刚可靠、开始 50 ms
角度渐变，计时器仍可能在过渡中到期并错误进入 `Fault`。

**修复**：获取计时器只覆盖真正等待可靠性的 `OpenLoopHold`；进入
`ObserverTransition` 时清零。若需要过渡 watchdog，使用独立计时器和独立故障码。
加入“在 timeout-1 tick 获取成功且完整过渡”的边界测试。

### FRT-009｜P2｜控制拍序号没有跨拍校验

`control_sequence` 目前只在相电压 eligibility 中用于
`control_sequence - phase_voltage_sequence == age_ticks`
（Rust `1551-1563`）。Controller 没有保存上一控制序号，也不拒绝重复、倒退或异常跳变。
目标端又用“成功输出次数”作为 sequence，而不是独立的 ADC conversion sequence。

**影响**：接口看似提供 stale/repeat 防护，实际只验证相电压样本的相对关系；CommandModel
路径对重复序号仍返回 OK。

**修复**：Controller 保存 `last_control_sequence` 和 initialized 标志，按 wrapping `+1`
规则校验；明确规定丢拍是立即 fault 还是受限容忍。平台使用独立 ADC 样本计数，不以
成功输出计数替代输入序号。为重复、跳号、回绕和故障恢复添加测试。

### FRT-010｜P2｜`actual_dt_s` 是“接受但不生效”的 ABI

V19 校验只要求 `actual_dt_s` 有限且大于 0（Rust `1497-1498`）；实际控制律在
`2762-2766` 固定使用 `1 / configured_pwm_frequency`。测试甚至故意传入 10 kHz 的 dt，
并断言与 legacy 12 kHz 结果逐拍相同（`4080-4100`）。目标当前传固定 12 kHz，所以没有
立即数值偏差，但字段名和验证语义会让后续调用者误以为抖动/丢拍已被处理。

**修复二选一**：

- 若保持固定周期算法，把字段改成 `expected_dt_s`，严格校验与配置周期的容差；或
- 真正消费有上下限的实测 dt，并一次性审查启动斜坡、PI、observer、超时和仿真，禁止
  只对部分算法使用变 dt。

### FRT-011｜P2｜心跳输出旧 Vbus

`applications/main.c:1611-1627` 先调用 `foc_platform_get_diagnostics()` 复制快照，随后
未 arm 时才调用 `foc_platform_read_feedback()` 更新全局诊断，最后却打印先前的局部
`diagnostics.bus_voltage_raw`。因此心跳至少落后一轮（5 s）；arm 后还叠加 `FRT-002`。

**修复**：未 arm 时先 read feedback，再 get diagnostics；或直接打印返回的 feedback。
心跳增加 Vbus valid/age，避免把旧数据表现成当前测量。

### FRT-012｜P2｜兼容 FFI 状态约束弱于正式入口

正式 `foc_rust_configure()` 要求 Disabled；但 `foc_rust_configure_basic()`
（Rust `2432-2467`）和 `foc_rust_configure_st_reference()`（`2488-2496`）没有同等状态门，
且仍在目标头文件公开。当前树内目标 C 没有调用它们，但未来调用者可在控制器活动时
重置参数和 observer，绕过正式实时路径的状态纪律。

**修复**：目标固件通过 feature/linker symbol allowlist 不导出测试兼容入口；如果必须
保留，所有配置入口统一要求 Disabled + 平台未 arm，并加入导出符号快照测试。

当前主要文件规模：

| 文件 | 行数 | 混合职责 |

### FRT-014｜P3｜ST STO 选择值实际运行 Float BEMF

`StStoPll` raw 值 2 被配置校验接受，但 `ConfigurableObserver` 把它和 Float BEMF 路由
到同一个 `bemf` 实例，并把可靠性固定为 false。Shell 也提供 `foc_cfg observer st`。
源码注释已说明这是保留槽，所以不是未披露的算法错误；问题在于遥测/配置名称可能让
比较者误以为已经运行 ST STO。

**修复**：实现前拒绝目标固件选择值 2；或明确显示
`ST_SLOT_EMULATED_BY_FLOAT_BEMF`，不允许以 `ST_STO_PLL` 名称输出实验结论。

### FRT-015｜P3｜Python/硬件工具依赖未锁定

Rust 有 `Cargo.lock`，当前外部依赖仅 `libm 0.2.16`；但 Python 工具没有
`requirements.txt`、`pyproject.toml` 或 lock。硬件串口工具依赖 `pyserial`，文档使用
未固定版本的 `pip install pyserial`。固定机器环境上的测试通过不能保证新机器复现。

**修复**：增加最小 `pyproject.toml`/lock，区分 core-test 与 hardware extra；CI 从空环境
安装并执行 `test.ps1` 中的 Python 部分，记录 Python 和依赖版本。

### FRT-016｜P3｜文档和注释漂移

- 架构文档仍把 Rust bridge 描述为约 1,810 行，当前实际为 5,021 行；
- `foc_realtime_timing` 注释把 32 位计数在 170 MHz 下的时间当作按 CPU cycle 增长，
  但实际计数按控制样本增长；12 kHz 下回绕约 4.14 天，不是约 25 秒；

这些不直接改变控制输出，但会误导评审、运维和容量判断。修复时应更新实际规模与计数
语义，并在脚本内设置明确的 UTF-8 进程环境；不要依赖操作者终端的全局配置。

## 6. 已有正向控制

以下机制真实存在且值得保留，但不能抵消上述问题：

- Calibration/Identification 在编译期禁止普通 motor arm；
- Rust/C ABI 有 `repr(C)`、size/offset 静态断言和 Host 对照；
- Rust 实时路径无动态分配，固定频率配置与目标交叉构建已覆盖 CPU/CORDIC 后端；

- Break 硬件链优先级高于 ADC ISR，driver fault 和软件过流都能快速关断；
- V19 Measured/Hybrid 当前保持 gate 关闭，未标定相电压不会进入 observer；
- Ls(I) 有独立 session/permit/preload/capture 约束；
- 生产参数候选、来源和未审批状态有较完整的证据链；
- 工程操作日志明确区分 S0～S6，不把 Host PASS 或交叉构建当作板端证明。

这些控制说明工程基础并不差；当前问题主要集中在“跨上下文事务”和“契约与实现之间的
最后一公里”，应优先修补，而不是推倒重写算法。

3. 建立 `FRT-003` 统一 fault latch/clear；
4. 在修复分支中暂时让 Diagnostic/Production arm 默认拒绝，直到目标寄存器测试通过。

**退出条件**：Host 寄存器模型的全部中断排列通过，目标板空载示波器证明中性首拍和
Break 后保持关断。

### 阶段 1：恢复保护闭环

1. 实现实时 Vbus 与 UV/OV（`FRT-002`）；
2. 固化板级不可放宽阈值（`FRT-004`）；
3. 修复启动 fail-open（`FRT-005`）；
4. 增加目标路径测试/HIL（`FRT-006`）。

**退出条件**：每一种保护故障都先关断、统一锁存、拒绝直接重启，只有恢复条件和显式
clear 全部满足后才能 re-arm。

### 阶段 2：修复状态与数据契约

依次处理观察器超时、sequence、dt、心跳和兼容 FFI（`FRT-008`～`FRT-012`），每项先
增加失败测试，再改实现。重新执行算法回归、仿真、四档构建和目标 WCET。

### 阶段 3：行为冻结后的架构拆分

按 `FRT-013` 拆模块；随后处理 ST 占位接口、Python lock、文档漂移和重复文档。
拆分阶段不改变控制参数，不与新 observer 算法开发混在同一提交。

## 9. 建议的完成判据

整改不能只以“能编译”“电机能转”结束。建议至少满足：

- P0/P1 每项都有可重复失败用例和修复后 PASS 用例；
- arm、stop、Break、fault clear 的状态转移图与代码一致；
- 每种硬件/软件故障只有一个锁存入口和一个受控清除入口；
- 实时输入的 current/Vbus/sequence/dt 都有来源、valid、age 和拒绝策略；
- Host 寄存器模型覆盖中断排列，HIL 覆盖真实 Break/driver/Vbus/current/deadline；
- 四构建档回归继续通过，目标板 WCET 保持批准裕量；
- S4～S6 证据单独记录，不用本报告的 S0～S2 结论代替；
- 修复后的代码和测试由另一名评审者复核，重点检查是否引入新的 arm/clear 旁路。

## 10. 最终结论

FluxRT 已具备较完整的参数证据、构建档、C/Rust ABI 校验、算法测试和安全文档，但当前
还不能据此认定为可安全继续带功率级验证。最优先的问题不是继续调 PI 或更换观察器，
而是把 **arm、output commit、fault latch/clear、实时 Vbus** 做成可证明的闭环事务。

在 `FRT-001`～`FRT-006` 关闭前，本项目应标记为：

> **软件回归与交叉构建通过；目标功率级安全门不通过，禁止把当前 PASS 解释成实机或
> 产品就绪。**
