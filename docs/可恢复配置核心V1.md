# FluxRT 可恢复配置核心 V1

## 1. 目的与完成边界

P3.1 把以后所有板卡、电机、功率级、Axis、输入源和标定数据放入一套可恢复、可迁移、
可审计的纯 Rust 配置核心。实现位于 `rust/crates/foc-control/src/config.rs`，保持
`no_std`、无堆、无锁、无文件系统和无 MCU 寄存器依赖。

本阶段已经完成：

- `BoardConfig`、`MotorConfig`、`InverterConfig`、`AxisConfig`、`AppConfig`、
  `CalibrationData` 六组定宽数据；
- 512 B 双槽记录、双 CRC、最后提交标记、32 位回绕序号；
- `candidate / approved / active` 分离、工厂默认回退、上一批准版本自动/手工回滚；
- schema V0 → V1 的内存迁移和未知版本拒绝；
- 写入每个字节点掉电、损坏 CRC、坏身份、序号歧义和回滚 Host 测试；
- 板号、电机号、反馈能力和标定有效位的最终 arm 校验入口。

本阶段明确**没有**实现：目标 Flash 擦写、RT-Thread 参数服务、C ABI、运行中改参、Shell
保存、上位机或 GUI。当前板上仍读取原来的编译期 profile，默认闭环和快环行为不变。

## 2. 六组配置的职责

| 分组 | 主要内容 | V1 最终校验责任 |
|---|---|---|
| `BoardConfig` | 板号、PWM/控制频率、ADC量程、采样换算、能力位 | Rust结构校验 + C平台实值复核 |
| `MotorConfig` | 电机号、极对数、Rs、Ld/Lq、磁链、电流和转速 | Rust；正式值仍需审批证据 |
| `InverterConfig` | 功率级号、电流/母线范围、死区、管压降、制动电阻 | Rust请求值 + C硬件上限 |
| `AxisConfig` | Axis ID、反馈源、方向、环路增益、软限位 | Rust |
| `AppConfig` | CAN/UART和最多4个命令来源的权限、优先级、lease、timeout | Rust命令仲裁策略 |
| `CalibrationData` | 电流零偏、相电压、编码器、Hall及板卡+电机绑定 | Rust有效位 + C采集/审批流程 |

`CalibrationData.valid_flags` 是数据是否存在的唯一依据。数值为 `0` 不表示“未标定”；
例如零偏恰好为零也可以是有效结果。未置有效位的字段必须使用规范零值，避免旧内存或半份
数据被误读成标定结果。

## 3. candidate、approved 和 active

```text
外部输入/辨识结果
        │ validate
        ▼
    candidate       只允许检查、比较，不参与启动
        │ 人工/设备端批准
        ▼
    approved        可作为启动候选，但仍要过硬件身份与 arm 门
        │ 启动选择 + Safe/Disabled 原子应用（P3.2）
        ▼
      active        当前运行周期只读
```

- 存储记录只包含 `Candidate` 或 `Approved`；`active` 是启动恢复决策，不是第三种可随意
  写入的持久化状态；
- 上电只从最新完整的 `Approved` 记录选择 active，最新 candidate 永远不会自动运行；
- 没有有效 approved 时使用调用者提供的不可覆盖 factory defaults；
- factory defaults 仍必须通过结构校验，而且不是“已完成电机标定”的证明；
- P3.2 才负责把恢复结果放入 pending，并只在 Safe/Disabled 状态提交到运行态。

## 4. 512 B 记录格式

每个槽固定为 512 B，小端编码。V1 payload 为 316 B；剩余区域保持擦除值 `0xFF`。

| 偏移 | 大小 | 字段 |
|---:|---:|---|
| 0 | 4 | magic `FRCF` |
| 4 | 2 | storage format version |
| 6 | 2 | schema version |
| 8 | 2 | header size（40） |
| 10 | 2 | payload size |
| 12 | 4 | generation sequence |
| 16 | 4 | Candidate/Approved |
| 20 | 4 | board ID 镜像 |
| 24 | 4 | motor ID 镜像 |
| 28 | 4 | payload CRC-32 |
| 32 | 4 | header+payload record CRC-32 |
| 36 | 4 | reserved，必须为0 |
| 40 | 316 | V1 canonical payload |
| 356…507 | 152 | 擦除保留区 |
| 508 | 4 | commit magic `CMIT`，永远最后写 |

CRC 使用 reflected CRC-32 多项式 `0xEDB88320`。payload CRC 用于快速定位内容损坏；
record CRC 还覆盖版本、状态、序号和身份。CRC 只做随机差错检测，不是身份认证或防篡改签名。

## 5. 原子写入和掉电恢复

保存由 `prepare_config_save()` 生成 `PreparedConfigWrite`，平台以后只能按以下顺序执行：

1. 确认 Axis 为 Safe/Disabled、PWM/MOE/gate 全部关闭；
2. 选择非当前 active 的槽；candidate 更新优先覆盖旧 candidate；
3. 擦除目标槽；
4. 写 40 B header 和 canonical payload；
5. 回读并检查两级 CRC（目标适配器阶段实现）；
6. **最后**写 4 B `CMIT`；
7. 再次解码，成功后才更新管理层状态。

任意一步掉电时：

- commit 不完整的槽必定无效；
- 当前 approved 槽在新 commit 完成前不会被覆盖；
- 新 commit 完成后，回绕 sequence 选择新记录；
- 最新记录损坏时自动使用另一槽的上一份 approved；
- 两个序号相同或相差恰好半区间时拒绝猜测，返回 `AmbiguousSequence`。

V1 的 Host 测试枚举了从擦除后到 commit 最后一个字节之前的每个写入中断点；所有中断
都继续选择旧 approved。完整写入后才切到新 approved。还逐字节构造了目标槽异常数据，
确认另一槽不受影响。

## 6. 双槽选择规则

| 操作 | 目标槽选择 | 必须保留 |
|---|---|---|
| 新 candidate | 旧 candidate；没有则无效/较旧槽 | 最新 approved |
| 新 approved | 当前 active 的另一个槽 | commit 完成前的 active |
| 手工 rollback | 把上一 approved 以新 sequence 写入当前 active 槽 | 上一 approved 原槽 |
| 启动恢复 | 最新有效 approved；否则 factory | candidate 不得激活 |

手工回滚不是简单“临时选择旧槽”。`prepare_config_rollback()` 会把旧配置写成更新一代，
所以再次重启仍保持回滚结果，并且整个回滚写入同样满足掉电原子性。

## 7. 版本迁移

storage format 与 payload schema 分开版本化：

- storage format 决定槽/header/commit 读取方法；未知版本直接拒绝；
- schema 决定 payload 字段。V1 当前能读取 V0，并为缺少的 bundle/group 版本补 V1 默认；
- 迁移只在 RAM 中产生 V1 `ConfigBundle`，返回 `migrated=true`；
- 设备端后续必须在停机事务中重新保存，不能在启动恢复路径里偷偷写 Flash；
- 未知新 schema fail-closed，旧固件不得猜测新字段。

目前项目历史上没有正式发布过 V0 Flash 数据，V0 是用来冻结迁移机制的测试基线，不代表
现有编译期 profile 已自动变成 approved 记录。

## 8. 校验分层

`ConfigBundle::validate()` 检查：

- 组版本、非零 identity、频率整除和已知能力位；
- 所有物理量有限、正负号和交叉范围合法；
- 电机连续电流不超过配置的功率级相电流上限；
- Axis/反馈枚举、方向、PI和软限位合法；
- 命令来源数量、唯一 ID、权限位、优先级和时间窗合法；
- 标定 identity 与 Board/Motor 一致，未生效字段保持规范零值。

`validate_for_arm(expected_board_id, expected_motor_id)` 在此基础上再检查：

- 实际板号和电机号必须匹配；
- ABZ/绝对编码器/Resolver/Fused 要求板卡 encoder 能力和 encoder 标定有效位；
- Hall 要求板卡 Hall 能力和 Hall 标定有效位；
- Sensorless 不凭空要求编码器标定，但仍受既有观察器、参数审批和平台安全门约束。

Rust 只能收紧软件请求。母线、过流、Break、驱动故障等硬件上限仍由 C 平台最终裁决，
持久化配置不能放宽硬件保护。

## 9. 后续接入方法

P3.2 设备端参数事务按以下固定方向接入：

```text
协议/Shell/Fake client
  -> begin + set 到 pending
  -> ConfigBundle::validate
  -> apply volatile（仅Safe/Disabled）
  -> rollback 或 commit
  -> prepare_config_save
  -> C Flash adapter 擦写/回读
  -> decode_config_slot 再验证
```

不允许：

- 在 12 kHz ISR 内编码、CRC、擦写或迁移；
- 从通信包直接覆盖 active；
- 把 candidate 当 approved；
- 在输出开启时写 Flash；
- 因 CRC 正确就跳过板号、电机号、范围、审批或平台能力检查；
- 让 GUI 成为唯一参数校验者。

## 10. 当前证据边界

P3.1 只达到 Host 单元测试和目标交叉编译的软件证据。若四档固件最终哈希不变，只能说明
未引用的配置核心被 section GC 排除；不能解释成板载 Flash 双槽已经存在。目标 Flash
扇区选择、擦写粒度、写后回读、掉电实测、磨损预算和 RT-Thread 管理线程属于后续阶段。
