# FluxRT 可恢复配置核心 V1

## 1. 目的与完成边界

P3.1 把以后所有板卡、电机、功率级、Axis、输入源和标定数据放入一套可恢复、可迁移、
可审计的纯 Rust 配置核心。P3.2A 在其上增加设备端参数事务骨架，P3.2B 再增加独立的
配置管理 C ABI 与无硬件 apply 执行器。核心实现位于 `rust/crates/foc-control/src/config.rs`
和 `config_transaction.rs`；ABI 位于 `foc-rt-bridge/src/config_abi.rs`，C 调度器位于
`foc/runtime/foc_config_apply_executor.c`。所有路径均保持无堆、无锁、无文件系统，并且不
进入 MCU 寄存器或 12 kHz ISR。

本阶段已经完成：

- `BoardConfig`、`MotorConfig`、`InverterConfig`、`AxisConfig`、`AppConfig`、
  `CalibrationData`和`ExternalIoConfig`七组定宽数据；
- V4当前记录为768 B双槽，兼容读取V0～V3旧记录；双 CRC、最后提交标记和32位回绕序号；
- `candidate / approved / active` 分离、工厂默认回退、上一批准版本自动/手工回滚；
- schema V0～V3 → V4 的内存迁移和未知版本拒绝；V0～V2的外部I/O全关闭，V3保留
  transport/link但关闭缺少标定的simple input；
- 写入每个字节点掉电、损坏 CRC、坏身份、序号歧义和回滚 Host 测试；
- 板号、电机号、反馈能力和标定有效位的最终 arm 校验入口。

P3.2A 已增加：

- `begin/set/validate/prepare apply/confirm apply/rollback/prepare commit/confirm commit`；
- 单写者 transaction token 和陈旧请求拒绝；
- 六组基础配置的定宽 patch 与真实 group diff；P2.4B2再扩为含External I/O的七组；
- `ManagementOnly/AxisRestart/PlatformRestart` 三类应用计划；
- 只有 Axis Disabled、功率输出关闭、无活动故障时才能应用或持久化；
- commit 回读失败保留已实际应用的 volatile active，并进入 `StorageFault`，禁止继续
  arm/改参；不能在纯状态机里假装外部控制器已经自动回滚。

P3.2B、P2.4B2及P2.5A2已增加：

- 独立于实时 bridge V22 的 `FOC_CONFIG_ABI_VERSION=V4`，增加simple input标定但不扰动快环布局；
- 固定 4 KiB、8 字节对齐的不透明管理上下文，以及七组定宽 C 结构和尺寸断言；
- begin/set/validate/apply/rollback/commit 全流程入口与细分错误码/错误详情；
- Platform → Axis → Management 固定顺序的无回调 C 执行器；失败会锁存，只有 Disabled、
  输出关闭且无活动故障时才能安全复位；
- Host Fake Flash 完整写入、写后回读、坏回读进入 `StorageFault` 并阻止 arm 的测试。
- `ExternalIoConfig`进入同一pending/diff/apply/commit事务，归类为Management action；
  配置失败保持旧active，V0～V2迁移补全关闭，V3迁移保留transport/link但关闭simple input。

P4.1C 已有一个默认关闭的反馈标定协调器会调用 config begin/stage/validate，并等待外部参数
服务完成 commit/readback；它不是完整参数服务。当前仍**没有**实现：目标 Flash 擦写、
RT-Thread 参数持久化服务、真实平台/控制器重建适配器、Shell 保存、上位机或 GUI。当前
板上仍读取原来的编译期 profile，默认闭环和快环行为不变。

## 2. 七组配置的职责

| 分组 | 主要内容 | V1 最终校验责任 |
|---|---|---|
| `BoardConfig` | 板号、PWM/控制频率、ADC量程、采样换算、能力位 | Rust结构校验 + C平台实值复核 |
| `MotorConfig` | 电机号、极对数、Rs、Ld/Lq、磁链、电流和转速 | Rust；正式值仍需审批证据 |
| `InverterConfig` | 功率级号、电流/母线范围、死区、管压降、制动电阻 | Rust请求值 + C硬件上限 |
| `AxisConfig` | Axis ID、反馈源、方向、环路增益、软限位、motion显式启用位与规划参数 | Rust |
| `AppConfig` | CAN/UART和最多4个命令来源的权限、优先级、lease、timeout | Rust命令仲裁策略 |
| `CalibrationData` | 电流零偏、相电压、编码器、Hall及板卡+电机绑定 | Rust有效位 + C采集/审批流程 |
| `ExternalIoConfig` | transport/input启用、四个link、四个simple input、来源策略和失效动作 | Rust结构校验 + C板级capability/资源复核 |

`CalibrationData.valid_flags` 是数据是否存在的唯一依据。数值为 `0` 不表示“未标定”；
例如零偏恰好为零也可以是有效结果。未置有效位的字段必须使用规范零值，避免旧内存或半份
数据被误读成标定结果。

### 2.1 外部通信与输入配置

V4保留`AppConfig`中的旧CAN节点号、UART波特率和最多4个命令来源策略，并将独立的
`ExternalIoConfig`升级为V2/384 B：除transport/input enable、link/input和来源策略外，新增
88 B `SimpleInputConfig`，持久化PWM/Analog中心标定及Step/Dir比例/零位/最大频率。它采用
“编译期Kconfig capability + 运行期配置enable”两级选择，并进入同一
candidate/validate/apply/commit/rollback事务。

512 B旧槽最大payload 468 B，V2已占340 B，只剩128 B，无法容纳该组；因此P2.4B2把当前
记录扩为768 B。P2.5A2的V4 payload为724 B，正好填满40～763；未建立非原子sidecar。
V0～V2旧记录仍从offset 508读取commit；V3/V4从offset 764读取commit。V3迁移保留
transport/link但把simple input全关闭。详见[P2.4B2报告](performance/2026-10-01-P2.4B2-统一配置与低频命令Owner.md)
和[P2.5A2报告](performance/2026-10-01-P2.5A2-输入配置与服务接线.md)。公共骨架和所有
物理接口仍默认关闭，配置进入持久化纯逻辑不等于目标Flash服务已接通。

## 3. candidate、approved 和 active

```text
外部输入/辨识结果
        │ validate
        ▼
    candidate       只允许检查、比较，不参与启动
        │ 人工/设备端批准
        ▼
    approved        可作为启动候选，但仍要过硬件身份与 arm 门
        │ 启动选择 + Disabled 原子应用（P3.2事务与目标中立执行计划）
        ▼
      active        当前运行周期只读
```

- 存储记录只包含 `Candidate` 或 `Approved`；`active` 是启动恢复决策，不是第三种可随意
  写入的持久化状态；
- 上电只从最新完整的 `Approved` 记录选择 active，最新 candidate 永远不会自动运行；
- 没有有效 approved 时使用调用者提供的不可覆盖 factory defaults；
- factory defaults 仍必须通过结构校验，而且不是“已完成电机标定”的证明；
- P3.2A 负责 pending/active 纯状态迁移和应用计划；P3.2B 已把它导出为 C ABI 并冻结
  分层执行顺序。P4.1C反馈协调器只消费事务的stage/validate边界；完整参数服务与真实适配器
  以后接入，各阶段均不允许在输出开启时应用。

## 4. 768 B V4记录与旧记录兼容

当前每个槽固定为768 B、小端编码，V4 payload为724 B。解码器仍接受V3的636 B，以及
V2/V1/V0的340/316/284 B旧payload；V0～V2按offset 508检查commit，V3/V4按offset 764。

| 偏移 | 大小 | 字段 |
|---:|---:|---|
| 0 | 4 | magic `FRCF` |
| 4 | 2 | storage format version |
| 6 | 2 | schema version |
| 8 | 2 | header size（40） |
| 10 | 2 | payload size |
| 12 | 4 | generation sequence |
| 16 | 4 | Candidate/Approved |
| 20 | 4 | board ID 镜像 |
| 24 | 4 | motor ID 镜像 |
| 28 | 4 | payload CRC-32 |
| 32 | 4 | header+payload record CRC-32 |
| 36 | 4 | reserved，必须为0 |
| 40 | 724 | V4 canonical payload（V3为636 B、V2为340 B、V1为316 B、V0为284 B） |
| 764 | 4 | V3/V4 commit magic `CMIT`，永远最后写 |

V0～V2旧记录的commit仍位于508；迁移测试明确检查V2的508位置有效而764保持擦除值。
V4没有payload保留空间；新增持久化字段前必须扩大槽、拆分存储或重构编码。

CRC 使用 reflected CRC-32 多项式 `0xEDB88320`。payload CRC 用于快速定位内容损坏；
record CRC 还覆盖版本、状态、序号和身份。CRC 只做随机差错检测，不是身份认证或防篡改签名。

## 5. 原子写入和掉电恢复

保存由 `prepare_config_save()` 生成 `PreparedConfigWrite`，平台以后只能按以下顺序执行：

1. 确认 Axis 为 Safe/Disabled、PWM/MOE/gate 全部关闭；
2. 选择非当前 active 的槽；candidate 更新优先覆盖旧 candidate；
3. 擦除目标槽；
4. 写 40 B header 和 canonical payload；
5. 回读并检查两级 CRC（目标适配器阶段实现）；
6. **最后**写 4 B `CMIT`；
7. 再次解码，成功后才更新管理层状态。

任意一步掉电时：

- commit 不完整的槽必定无效；
- 当前 approved 槽在新 commit 完成前不会被覆盖；
- 新 commit 完成后，回绕 sequence 选择新记录；
- 最新记录损坏时自动使用另一槽的上一份 approved；
- 两个序号相同或相差恰好半区间时拒绝猜测，返回 `AmbiguousSequence`。

V1 的 Host 测试枚举了从擦除后到 commit 最后一个字节之前的每个写入中断点；所有中断
都继续选择旧 approved。完整写入后才切到新 approved。还逐字节构造了目标槽异常数据，
确认另一槽不受影响。

## 6. 双槽选择规则

| 操作 | 目标槽选择 | 必须保留 |
|---|---|---|
| 新 candidate | 旧 candidate；没有则无效/较旧槽 | 最新 approved |
| 新 approved | 当前 active 的另一个槽 | commit 完成前的 active |
| 手工 rollback | 把上一 approved 以新 sequence 写入当前 active 槽 | 上一 approved 原槽 |
| 启动恢复 | 最新有效 approved；否则 factory | candidate 不得激活 |

手工回滚不是简单“临时选择旧槽”。`prepare_config_rollback()` 会把旧配置写成更新一代，
所以再次重启仍保持回滚结果，并且整个回滚写入同样满足掉电原子性。

## 7. 版本迁移

storage format 与 payload schema 分开版本化：

- storage format 决定槽/header/commit 读取方法；未知版本直接拒绝；
- schema 决定payload字段。V4能读取V0～V3；V0缺少的bundle/group版本补当前默认，
  V0/V1缺少的motion字段统一补`enabled=0`和五个零值，V0～V2缺少的外部I/O组补全关闭；
  V3没有simple input标定，所以只保留transport/link并强制关闭所有simple input；
- 迁移只在RAM中产生V4 `ConfigBundle`，返回`migrated=true`；
- 设备端后续必须在停机事务中重新保存，不能在启动恢复路径里偷偷写 Flash；
- 未知新 schema fail-closed，旧固件不得猜测新字段。

目前项目历史上没有正式发布过 V0 Flash 数据，V0 是用来冻结迁移机制的测试基线，不代表
现有编译期 profile 已自动变成 approved 记录。

## 8. 校验分层

`ConfigBundle::validate()` 检查：

- 组版本、非零 identity、频率整除和已知能力位；
- 所有物理量有限、正负号和交叉范围合法；
- 电机连续电流不超过配置的功率级相电流上限；
- Axis/反馈枚举、方向、PI和软限位合法；
- 命令来源数量、唯一 ID、权限位、优先级和时间窗合法；
- 外部transport/input已知位、link/input结构、来源ID唯一性、权限、控制模式和失效动作合法；
- 标定 identity 与 Board/Motor 一致，未生效字段保持规范零值。

`validate_for_arm(expected_board_id, expected_motor_id)` 在此基础上再检查：

- 实际板号和电机号必须匹配；
- ABZ/绝对编码器/Resolver/Fused 要求板卡 encoder 能力和 encoder 标定有效位；
- Hall 要求板卡 Hall 能力和 Hall 标定有效位；
- Sensorless 不凭空要求编码器标定，但仍受既有观察器、参数审批和平台安全门约束。

Rust 只能收紧软件请求。母线、过流、Break、驱动故障等硬件上限仍由 C 平台最终裁决，
持久化配置不能放宽硬件保护。

## 9. P3.2 参数事务、管理 ABI 与后续接入

P3.2 当前软件架构按以下固定方向工作：

```text
协议/Shell/Fake client
  -> begin(token) + group patch 到 pending
  -> ConfigBundle::validate
  -> prepare volatile apply（计算diff与应用等级）
  -> C executor依次发出Platform/Axis/Management动作
  -> 各所有者适配器处理pending bundle（目标实现仍待接）
  -> confirm volatile apply（仅Disabled、输出关闭、无故障）
  -> rollback 或 prepare commit
  -> prepare_config_save
  -> C Flash adapter 擦写/回读
  -> decode_config_slot 再验证并confirm commit
```

具体电机的 `Rs/Ld/Lq/磁链/PI/观察器` 数值不属于事务状态机。它们以后通过 `MotorConfig`
或 `AxisConfig` patch 修改，仍需各自的仿真、审批和实机证据；架构代码不为当前电机写死数值。

P3.2B 已完成以下目标中立适配，不重写事务语义：

1. C/Rust管理ABI把定宽请求转换为七组patch，不允许字符串或配置事务进入ISR；
2. C执行器依据group diff发出Platform、Axis、Management动作，并强制由外到内排序；
3. Rust以定宽写步骤导出双槽写计划，Host Fake Flash执行擦除、逐字写入、回读和确认；
4. 任何动作失败都不能调用confirm；坏Flash回读保留volatile active但进入StorageFault；
5. P4.1C反馈协调器仍默认关闭且未注册目标实例；没有连接真实Flash、参数持久化任务、平台
   动作或运行电机。

配置子ABI单独使用V4（Axis 68 B、Bundle 732 B，含384 B External I/O组），上下文上限
为4 KiB；当前实时`FOC_RUST_ABI_VERSION=V22`。配置调用者必须由一个
管理线程串行拥有上下文；ABI没有函数表或回调，执行器也不直接调用Rust，因此不会形成
C/Rust重入或把平台所有权倒置。

不允许：

- 在 12 kHz ISR 内编码、CRC、擦写或迁移；
- 从通信包直接覆盖 active；
- 把 candidate 当 approved；
- 在输出开启时写 Flash；
- 因 CRC 正确就跳过板号、电机号、范围、审批或平台能力检查；
- 让 GUI 成为唯一参数校验者。

## 10. 当前证据边界

P3.1/P3.2/P2.4B2只达到Host单元测试、闭环仿真回归和目标交叉构建的软件证据。配置ABI符号在
Rust目标库中存在，C执行器和外部I/O管理适配器也已通过测试，但完整设备服务尚未从`main`引用；因此不能解释
成板载参数事务或Flash双槽已经可用。目标Flash扇区选择、擦写粒度、掉电实测、磨损预算、
真实控制器/平台动作和RT-Thread管理线程属于后续目标集成任务。
