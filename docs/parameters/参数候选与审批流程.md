# 参数候选、证据与 Production Profile 审批流程

## 1. 目的

本流程把“改参数”拆成四件不同的事：提出候选、机器复核、人工审批、固件集成。工具只
能完成前两件，不能自动批准，也不会修改 `applications/foc_production_profile.c`。

当前基线是：

- 候选：`profiles/candidates/rev1-gbm2804h-unapproved.json`；
- 板卡：NUCLEO-G431RB + X-NUCLEO-IHM16M1；
- 电机：GBM2804H-100T；
- runtime CRC：`0x8C7A8DF4`；record CRC：`0xD9F996C3`；
- 参数审批和闭环审批均为 `false`，`closed_loop_enable=0`。

## 2. 文件职责

| 路径 | 职责 | 是否进入固件 |
|---|---|---|
| `profiles/schema/fluxrt-production-profile-v1.schema.json` | 编辑器和审计使用的 v1 格式契约 | 否 |
| `profiles/candidates/*.json` | 完整 60 字运行配置、目标身份、审批和预期 CRC | 否 |
| `profiles/generated/*.inc` | 工具生成、等待人工复核的 C 初始化片段 | **否，默认不编译** |
| `tools/foc_profile_tool.py` | 严格字段检查、CRC、证据哈希与候选片段生成 | 否 |
| `rust/.../examples/export_runtime_config.rs` | 从 Rust 默认值导出实际配置和 CRC，避免凭文档猜值 | 否 |
| `applications/foc_production_profile.c` | 经评审后人工集成的唯一固件只读档案 | 是 |

Python 工具验证记录格式、ABI 字序、CRC 和审批证据。最终运行参数的物理范围和状态机
约束仍由 Rust `foc_rust_configure()` 校验；两道校验不能互相替代。

## 3. 日常命令

在工程根目录执行：

```powershell
# 查看 Rust 当前实际默认值和 runtime CRC
cargo run --manifest-path rust/Cargo.toml --package foc-rt-bridge `
  --example export_runtime_config --locked

# 校验候选
python tools/foc_profile_tool.py verify `
  profiles/candidates/rev1-gbm2804h-unapproved.json

# 生成等待评审的 C 片段；不会修改固件源码
python tools/foc_profile_tool.py generate `
  profiles/candidates/rev1-gbm2804h-unapproved.json `
  --output profiles/generated/rev1-gbm2804h-unapproved.inc

# CI/回归只检查生成物是否过期，不写文件
python tools/foc_profile_tool.py generate `
  profiles/candidates/rev1-gbm2804h-unapproved.json `
  --output profiles/generated/rev1-gbm2804h-unapproved.inc --check

# 全套主机回归
.\test.ps1
```

## 4. 候选生命周期

```text
复制上一 revision
  → 修改候选参数和 revision
  → 重新填写 expected CRC
  → verify + test.ps1
  → 参数证据齐全并人工审批
  → 闭环证据齐全并单独人工审批
  → generate 得到候选 C 片段
  → 人工复核 diff 后集成到固件
  → 目标构建、烧录、受限实机、Production S6
```

规则：

1. 任何运行字段变化都必须增加 `profile.revision`，旧 CRC 必须失效；
2. `approved_runtime_config_crc32` 将审批绑定到确切的 240 B 配置；配置变化后不能沿用旧
   审批；
3. 每份证据必须是工程内相对路径，并记录真实 SHA-256；文件不存在、哈希变化或通过
   `..`/绝对路径越界都会拒绝；
4. `closed_loop.approved=true` 时，`parameters.approved` 必须同时为 true，并且
   `runtime_config.closed_loop_enable` 必须为 1；否则硬拒绝；
5. unapproved scope 必须保持 reviewer、时间、绑定 CRC 为 `null`，evidence 为空；
6. `.inc` 只是候选，不在 SConscript/CMake 中；生成成功不等于参数或闭环已批准。

候选的 `expected` 字段需要填入新计算值。安全做法是先保留旧值运行 `verify`，从错误中
核对新 runtime CRC；更新后再次运行工具并由第二人复核 diff。不能只为了让测试变绿而
改 CRC。

## 5. 审批证据最低集合

### 5.1 参数审批

至少包含以下 `kind`，每项都带路径和 SHA-256：

| kind | 内容 |
|---|---|
| `parameter-identification-raw` | 原始电压、电流、温度、转速和工况数据 |
| `parameter-identification-report` | Rs/Ld/Lq/磁链估计、重复性和适用温度范围 |
| `review` | 评审结论，明确 revision 与 runtime CRC |

参数审批只说明候选参数来源可追溯，不自动允许观测器接管。

### 5.2 闭环审批

至少包含：

| kind | 内容 |
|---|---|
| `independent-truth` | 编码器/测速仪等独立真值与内部估计的误差 |
| `fault-injection` | 失锁、过流、欠压、采样异常等安全退出验证 |
| `long-run` | 指定电压、限流、负载、温度和时长的长测记录 |
| `review` | 评审结论，明确 revision 与 runtime CRC |

当前没有独立测速/角度真值，所以不得把内部估速、仿真或“电机能转”填成
`independent-truth`。

## 6. 新候选最小操作

1. 复制 revision 1 JSON 为新的明确文件名；
2. `profile.revision` 加一，先保持两个审批为 false；
3. 修改完整运行配置，不直接编辑生成 `.inc`；
4. 运行 Rust exporter，确认基线字段和工具输入没有抄写漂移；
5. 更新两个 `expected` CRC，运行 `verify`、`--check` 与 `test.ps1`；
6. 把原始数据、报告和评审记录纳入工程，再填写其哈希；
7. 审批必须由明确 reviewer 和 UTC 时间完成；
8. 最后才把生成片段与固件档案做人工 diff，并按目标构建/实机流程验证。

如果只是实验候选，停在第 5 步即可，不得修改当前固件审批位。

实际辨识 session、原始证据和“证据不足时拒绝候选”的规则见
[`参数辨识采集与筛查流程.md`](参数辨识采集与筛查流程.md)。
