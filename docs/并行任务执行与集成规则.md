# FluxRT 并行任务执行与集成规则

## 1. 目的

FluxRT 后续工作不再机械地按单线串行推进。只要任务不共享写入点、不改变同一 ABI，且能在
PC 上独立验收，就可以并行实施；涉及目标板、功率级、同一份公共接口或最终参数批准的工作，
仍由主线串行集成。

并行的目标是缩短等待时间，不是绕过阶段依赖。Host、仿真、交叉构建和实机证据仍按
《工程操作日志》的 S0～S6 等级分别记录，任何一路 `PASS` 都不能替代另一等级的证明。

## 3. 可以并行的任务

- 只读源码/ABI/参数审计；
- 新建独立纯函数模块及其定向 Host 测试；
- 不连接串口、不烧录的 PC 仿真、故障注入和数据分析；
- 不写公共 schema 的报告生成器和回归测试；
- 互不重叠文档章节的证据整理。

这些任务开始前必须约定输入、输出、单位、枚举值和文件所有权。子路线不能自行修改共享构建
入口或把候选功能接入默认控制链。

## 4. 必须串行的任务

- 修改 `foc_rust_bridge.h` 与 Rust `#[repr(C)]` 结构；
- 提升 ABI/config/trace/schema 版本；
- 修改公共 CMake、SCons、Cargo feature 或生成配置；
- 接入目标 ISR、ADC/PWM 时序、关断与故障路径；
- 使用同一块板卡、串口、调试器、电源或电机的实机试验；
- 将候选参数写入 profile、批准参数或默认闭环路径；
- 合并、提交、推送和发布。

这些操作只有集成主线能够执行。原因是它们会同时影响多个消费者，或者需要唯一的硬件状态，
并行写入会让测试结果无法归因。

## 5. 每轮集成门

每轮并行结果按固定顺序收口：

1. 核对每条路线只修改了声明的独占文件；
2. 统一枚举、单位、状态优先级和 fail-closed 语义；
3. 由主线修改共享构建入口；
4. 先跑各路线的最小定向测试，再跑 `test.ps1`；
5. 目标代码有变化时再做相应档位交叉构建、size/map 和 WCET；
6. 更新阶段计划、架构分配和工程操作日志；
7. 需要实机的内容另开受限门，不从 PC 结果直接升格。

任一路失败只阻断依赖它的集成，不要求停止其它独立路线。失败原因和未完成边界同样写入操作
日志，不能为追求“全部并行完成”而弱化断言或默认回退。

## 6. 当前共同语义

- `CommandModel`：始终可用的安全默认观察器电压源；
- `Measured`：只有逐板标定、质量有效且样本年龄合格时才可选择；当前尚未授权；
- `Hybrid`：正常时可使用或融合测量值，任一质量门失败立即选择 `CommandModel`；当前只验证
  选择/回退契约，不接入快环；
- 原始 ADC 码只属于 C 平台/诊断层，Rust 快照只允许接收已换算的物理量与显式有效位；
- “未配置”和“未标定”不是数值为零，必须用状态/有效位表达；
- 恢复必须连续满足配置的 good-sample 数，故障进入也使用确定阈值，避免每拍抖动；
- 任何未知枚举、错误尺寸、旧版本或非有限物理量都 fail-closed。

## 7. 后续扩展方式

阶段计划中的任务可以标注为“并行候选”，但只有满足以下条件才能分流：输入已经冻结、输出可
独立验证、写入文件无重叠、失败不会改变硬件安全状态。否则保持串行。每次分流都在本文件的
“当前并行批次”表中写清边界，并在《工程操作日志》记录实际执行与合并结果。
