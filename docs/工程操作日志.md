## 3. 强制记录规则

### 3.1 哪些操作必须记录

- 新增、删除、移动或修改源码；
- Kconfig、`.config`、CMake、SCons、Cargo、链接脚本和依赖变化；
- 电机、控制器、观察器、保护、时序和硬件参数变化；
- 文档、接口、CSV schema、MATLAB/Simulink 模型变化；
- 格式、静态检查、Host 测试、交叉构建和 size/map 检查；
- 仿真、参数扫描、数据清洗和绘图；
- 烧录、串口操作、示波器测量和电机实机运行；
- Git 初始化、分支、提交、合并、revert、tag 和发布包；
- 失败、回退、临时绕过和没有完成的尝试。

只读查看如果没有形成新判断，可以不单独建记录；如果查看改变了项目结论、参数判断或
下一步方案，也应记录。

### 3.2 证据等级必须分开

| 等级 | 含义 | 不能证明 |
|---|---|---|
| S0 | 设计/源码静态检查 | 能编译或能运行 |
| S1 | 格式、lint、单元测试、Host 测试 | 目标 MCU 可链接或实时性满足 |
| S2 | STM32 交叉构建、size/map | 已成功烧录或硬件正常 |
| S3 | PC/MATLAB/Simulink 仿真 | 实机与模型一致 |
| S4 | 成功烧录、启动和通信 | 功率级或电机已安全运行 |
| S5 | 受限低功率实机验证 | 全工况、长期或量产可用 |
| S6 | 故障注入、长测、多样本和独立真值 | 未覆盖条件下仍一定安全 |

记录中必须写实际达到的等级，不能用 `PASS` 笼统替代。

### 3.3 Git 关联规则

当前项目已经纳入 Git。每条记录至少包含：

- 开始分支和 `base commit`；
- 关联的实现提交；
- 工作树是否仍有未提交修改；
- 若创建里程碑 tag，记录真实 tag；
- 可执行的回退方式。

推荐两种方式：

1. **同提交记录**：代码、测试和本条日志一起提交。日志中的“结果提交”写
   `本条记录所在提交`，实际哈希用 `git log -1 -- docs/工程操作日志.md` 查询；
2. **实现提交 + 日志提交**：先提交实现，再在日志中写入实现哈希并提交日志。适合实机
   结果需要在实现提交之后补充的情况。

不要为了填写日志而修改已经存在的提交；不要使用破坏性 reset 作为常规恢复方式。
优先使用：

```powershell
git show <commit>
git diff <base>..<result>
git switch -c recovery/<name> <known-good-commit>
git revert <bad-commit>
```

具体操作前仍要检查工作树，保护用户未提交的修改。

#### 逆向结论（逐行取自官方源码，非推测）

| 项 | 结论 | 出处 |
|---|---|---|
| CRC-4 | `x^4+x+1`，覆盖头部低 28 位，结果放 bit 28-31 | `Src/aspep.c` |
| 头部位域 | type=bit0-3、length=bit4-16、pktnum=bit12-27 | TX/RX 两侧互相印证 |
| 数据段 CRC | **官方未实现的桩**：写死 `0xCA 0xFE`，必须协商成 0 | `aspep.c` `/* TODO */` |
| 握手方向 | **控制端必须先发 BEACON**；固件从不主动发包 | `ASPEP_start` 只配置接收 |
| 能力判定 | `version`/`DATA_CRC`/`TXS`/`TXA` 严格相等，仅控制端 `RX` 可更大 | `ASPEP_CheckBeacon` |
| 固件能力值 | `DATA_CRC=0`、`RX=7`、`TXS=7`、`TXA=32` | `mcp_config.c` |
| 命令码 | `GET_DATA_ELEMENT=0x10`、`SET=0x08`、`START_MOTOR=0x18` 等 | `mcp.h` |
| 寄存器类型 | `TYPE_DATA_8/16/32/STRING=1/2/3/4 << 3` | `register_interface.h` |
| `SC_NOMINAL_SPEED` | **官方两处定义冲突**：固件 16 位 vs Motor Pilot 清单 S32；实机按 16 位可用 | 实测 |

#### 关键发现：磁链量纲与物理口径差约 7 倍

`Ke` 的官方单位是**线电压 RMS**（`pmsm_motor_parameters.h` 注释
"Volts RMS ph-ph /kRPM"），换算相磁链应为
`flux = Ke/sqrt(3)*sqrt(2) / (1000*2*pi/60)`，该式也被 MCSDK 自己的
`MAX_BEMF_VOLTAGE = RPM*1.2*Ke*sqrt(2)/(1000*sqrt(3))` 印证。

但工程现值 `0.034739897 / (2*pi) = 0.005529026 Wb` 比这个物理口径**小约 7 倍**：
`Ke = 5.0` 按官方单位应得 `0.038985 Wb`。观测器的反电势幅值与滑模增益都按磁链
标度，这个偏差与工程记录的"观测器无法收敛"现象方向一致。

**尚未判定**：`MOTOR_VOLTAGE_CONSTANT = 5.0` 与注册表里的
`M1_MOTOR_RATED_FLUX = 5.0` 是否真是同一个物理量，无法从工程内确认。必须用一次
**实物反电势测量**（已知转速下测开路相电压）才能定论。转换工具因此**强制要求显式
指定 `--flux-convention`**，并把两种口径与相对基线的倍数差全部打印，绝不静默选一。

#### 未解决：实机握手被拒（本轮用调试器定位到具体位置）

**已排除的因素**（证据如下，不再是推测）：

| 项 | 证据 | 结论 |
|---|---|---|
| CRC 算法 | 我的 `crc4_check` 对**设备自己发的**头部 `0xC004040F` 通过；`crc4_header` 对**我发的**头部 `0xB0000045` 也自洽 | 算法正确，**不是** CRC 问题 |
| 错误上报 | 坏 CRC 帧回错误码 **4**；长度 8191 的 DATA_PACKET 回错误码 **2** | 设备错误上报**语义正确且能区分** |
| UART 参数 | 固件 `huart2`：`1843200 / 8B / 1 stop / no parity / 无流控`；实测 `USART2 CR1=0x4D`（UE/RE/TE 全开）、`CR3=0xC1`（DMAR/DMAT 开） | 与我的配置**完全一致** |
| 时钟与中断 | `RCC_APB1ENR1` USART2EN=1；`NVIC ISER1` bit6（USART2_IRQn=38）已使能；DMA1_Ch1 IRQ 已使能 | 中断通路已配置 |

**定位到的实际故障点**：用 OpenOCD + GDB 读目标内存与寄存器，得到

```text
DMA1 ch1: CCR=0x00000090  EN=0  NDTR=0     <- 接收通道未武装、无待收字节
aspepOverUartA: ASPEP_State=0 (IDLE)  TL_State=0  badPacketFlag=0  syncPacketCount=0
```

`NDTR=0` 表示接收 DMA **没有处于等待接收状态**，因此主机发来的负载字节不会被搬进
`rxHeader`，`ASPEP_HWDataReceivedIT` 也就永远不会被调用（断点从未命中，实测确认）。
`ASPEP_State` 恒为 IDLE 且 `syncPacketCount=0`，说明整个会话从未开始过。

这也解释了此前观察到的两种"矛盾"现象：

- 为什么会看到错误码：那些 NACK 是设备在坏帧 / 不完整帧之后由
  `ASPEP_RXframeProcess` 按源码逻辑发出的，上报本身是正常的；
- 为什么"同一个 CRC 验自己通过、验我的被拒"：并非 CRC 差异，而是我的帧**根本没被
  接收**，设备报的是它此前积累的错误状态。

**当前状态**：设备已完全静默（多种等待窗口下静默与发帧后均无字节）。需要**断电重新
上电**才能恢复到干净状态；调试器挂载也可能把它留在了异常态。恢复后应立即重试一次
握手，以区分"固件进入异常态后不恢复"与"我的客户端仍有问题"。
