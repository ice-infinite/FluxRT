# FluxRT 后续任务阶段计划

## 1. 文档用途

本文是 FluxRT 从既有基线到后续产品化的统一执行清单，用来直接回答：以前完成了什么、
证据在哪里、下一步是什么、前置条件是什么、是否需要转电机、怎样才算完成。后续每完成一个阶段，都必须同时更新本文状态和
[工程操作日志](工程操作日志.md)。

三个编号体系含义不同：

- 本文 `A0～A28`：按实际整改时间连续排列的**执行批次**；
- [整改架构与职责分配](整改架构与职责分配.md)中的 `A0～A9`：长期**架构工作包**；
- [ST与VESC工程改进路线图](ST与VESC工程改进路线图.md)中的“阶段 0～8”：长期
  **技术方向**。

执行批次可以同时覆盖多个架构工作包，但不能改变各层职责。本文是进度入口，技术原理
仍以整改路线、架构分配和对应性能报告为准。

## 3. A0 之前的工程基础

进入性能整改编号前，工程已经完成以下基础工作：

- 建立 NUCLEO-G431RB + X-NUCLEO-IHM16M1 的 RT-Thread 工程，使用 24 MHz HSE、
  32.768 kHz LSE 和 170 MHz 系统时钟；
- 建立 C 平台/HAL/ISR 与 Rust `no_std` 控制/算法分层，接入基础 FOC、Rev-Up、
  SMO/PLL、PI、SVPWM 和安全启停；

- 建立 Rust PC、MATLAB/Simulink 与实机 trace 的相关性框架；
- 项目统一更名为 FluxRT，连接 GitHub，并建立整改路线、架构分配和持续操作日志。

这些工作是后续 A0～A28 的前置基线，不代表闭环、观察器、参数或产品化已经完成。详细

## 5. A18：Calibration 构建档与数据契约

状态：**已完成（S1/S2；未烧录）**。结果和三档哈希见
[A18 专项报告](performance/2026-09-24-A18-Calibration构建档与标定契约.md)。

### 目标

建立 `Diagnostic / Calibration / Production` 三档，后续辨识和高频缓冲放入 Calibration，
避免继续把 Diagnostic 塞到 128 KiB Flash 极限。三档必须共用相同的关断、过流、deadline、
输出复核和默认不启动规则。

### 实际落点

- `build.ps1`、`custom.cmake`：新增并隔离构建目录；
- `foc/include/foc_build_profile.h`：集中校验三选一主宏并派生能力；共享 Kconfig 继续只管
  硬件/算法选项，避免三档通过同一 `.config` 串档；
- `applications/`：Calibration 只提供停机标定命令，不恢复任意运行期调参；
- `foc/platform/stm32g431/`：只编入所需 ADC/固定窗能力；
- `profiles/calibration/`：规划保存板卡标定记录、版本、温度和证据哈希。

### 完成门

1. 三个构建目录不能互用 CMake cache 或 Rust 静态库；
2. 三档均通过 Host、Rust、交叉构建和 size/map；
3. Calibration 上电仍保持输出关闭，必须显式进入标定状态；
4. Production 继续不包含 4 KiB 固定窗和标定 Shell；
5. 记录三档 BIN 哈希、ROM/RAM 和功能矩阵；
6. 不烧录、不运行电机即可完成本阶段。

以上六项均已满足。Calibration 的目标板停机确认和真实多点数据属于 A19，不回填为 A18
证据。

## 18. 与通用产品化路线的关系

A0～A28 继续负责当前 `NUCLEO-G431RB + X-NUCLEO-IHM16M1 + GBM2804H-100T`
参考组合的控制链、参数、实时性、闭环和实机证据，编号和完成标准保持不变。

FluxRT 后续向 VESC / ODrive 类型的通用控制器演进时，使用独立的 U0～U11 路线：

- U0 承接当前审计和 A 阶段尚未关闭的安全/实机门；
- U1～U3 建立 Axis、控制/输入模式、命令仲裁和持久化配置；
- U4～U5 增加反馈源、转矩/速度/位置和轨迹；
- U6～U9 增加通信、上位机、热/能量管理和升级；
- U10～U11 完成多板/多轴和产品化验证。

完整架构、依赖和 Rust PC + MATLAB/Simulink 双仿真契约见
[FluxRT 通用 FOC 产品架构与双仿真路线图](FluxRT通用FOC产品架构与双仿真路线图.md)。
U6 的自有上位机、在线调参、实时波形和设备协议细化见
[FluxRT Studio 上位机架构与调参可视化设计](FluxRTStudio上位机架构与调参可视化设计.md)。
A 路线的仿真、构建或实机 PASS 不能自动关闭 U 路线的产品能力门；U 路线新增的抽象也
不能回头覆盖 A 路线已有的实测边界和历史结论。

## 19. 统一后续任务总表

### 19.1 调度原则

从本节开始，A/FRT/U/FluxRT Studio/双仿真不再各自维护互相冲突的“下一步”。执行顺序统一为：

1. 先把当前大批未提交整改形成可复核基线，避免后续结果无法归因；
2. 目标安全链是 U0 主线，但等待硬件窗口时不阻塞纯软件工作；
3. `Axis/MotorService` 公共契约先串行冻结，随后优先完成命令、配置、反馈、基础控制和双仿真；
4. 按当前用户优先级，先完成外部控制/通信公共层、简单输入、Native和第三方协议的软件骨架；
5. 通信稳定后补未来上位机所需的**设备端**管理消息和Fake client，再回到热/再生、高级FOC等此前细节；
6. 真正的FluxRT Studio、Host SDK、页面、真实连接和参数编辑放在产品功能主体完成后的最后阶段；
7. 纯软件通信骨架可以先行，但任何目标启用、无功率板测或powered验证仍必须满足P0安全门；
8. 高级功能仿真通过只代表S3软件门，实机启用仍需单独S4～S6证据，不能提前写成实机完成；
9. 任何修改共享 C ABI、schema、构建入口、目标 ISR、配置版本或默认行为的工作都回到集成主线串行合入。

状态只使用“待开始、进行中、已完成、阻塞”。“等待某一仪器”只阻塞依赖该仪器的子任务，
不能把整个项目标成阻塞。
